# `create_verifier` — interaction spec

Branch contract for the `factory` module of the `verifier` module of `apps/harness-crypto`: the verifier family's construction point, which selects the concrete the configuration names, admits its composition through `harness-crypto/verifier/admit_verifier_composition` over the member identifier the selected declaration names and the declarations of the resolved chain forms, the chain adapter, the borrowed encoder, the selected pairing, and the selected generate member before anything is constructed, admits the delivery-statement version the params carry against the selected declaration, constructs the concrete over the borrowed pairing, chain, and delivery proof adapters and the deployed location the params carry, and hands it to a consumer generic over the family's trait for that delivery proof adapter. Each branch states condition, decision, dependency call, and the exact return outcome.

## `create_verifier<'a, P: IPairingAdapter, C: IChainAdapter, D: IDeliveryProofAdapter<Pairing = P, Forms = <C as IEntitlementStateAdapter>::Forms>, K: IVerifierConsumer<D>>(deps: &CreateVerifierDeps<'a, P, C, D, K>, params: CreateVerifierParams, payload: CreateVerifierPayload) -> CreateVerifierReturn<K::Output>`

The trusted form.

Declaration: the decision is an exhaustive `match` on `&params.concrete`, so a variant with no arm fails to compile — the `Evm { .. }` arm yielding `<EvmVerifier<'a, P, C, D> as IVerifierAdapter>::DECLARATION` and, under `#[cfg(any(test, feature = "mocks"))]`, the `Mock(failure_mode)` arm yielding the failure mode and `<MockIVerifierAdapter<'a, D> as IVerifierAdapter>::DECLARATION`. The composition admission below runs once against the declaration's `identifier` and the received declarations, and the version admission then runs against the declaration the arm yields.

| Branch | Condition | Decision | Dependency call | Outcome |
|---|---|---|---|---|
| incompatible composition | the call `(deps.admit_verifier_composition)(&ADMIT_VERIFIER_COMPOSITION_DEPS, AdmitVerifierCompositionParams { identifier: declaration.identifier }, AdmitVerifierCompositionPayload { chain_forms: &<<C as IEntitlementStateAdapter>::Forms as IChainForms>::DECLARATION, chain: &C::DECLARATION, encoder: deps.encoder, pairing: &P::DECLARATION, generate: deps.generate })` returns `Err` | none of this function's | the family's composition admission, once, before the version is read and before any construction | `Err(CreateVerifierErrorReturn::Composition(error))` carrying `AdmitVerifierCompositionErrorReturn` unchanged, with nothing constructed and the consumer not called; otherwise the function proceeds |
| unsupported statement version | the declaration's `statement_versions` does not contain `params.statement_version` | slice membership | none | `Err(CreateVerifierErrorReturn::UnsupportedStatementVersion { version })`, `version` the params'; nothing constructed and the consumer not called |
| constructor refused | the composition and version are admitted and `EvmVerifier::try_new` returns `Err(error)` | the selected concrete's constructor runs once | `EvmVerifier::try_new(EvmVerifierConstructorParams { pairing: deps.pairing, chain: deps.chain, delivery_proof: deps.delivery_proof, verifier_address: params.verifier_address, settings: *settings })` | `Err(CreateVerifierErrorReturn::Evm(error))`, the refusal unchanged and the consumer not called |
| admitted | `try_new` returns `Ok(adapter)` | the adapter moves into the consumer's payload | `deps.consumer.consume_verifier(ConsumeVerifierParams, ConsumeVerifierPayload { adapter })`, exactly once | `Ok(CreateVerifierSuccessReturn { output })` holding the consumer's output |

`Mock(failure_mode)` arm, under `#[cfg(any(test, feature = "mocks"))]`: the same composition admission over `<MockIVerifierAdapter<'a, D> as IVerifierAdapter>::DECLARATION`'s `identifier` and the received declarations, then the same `statement_versions` admission against `params.statement_version`, each read before any construction and each refusal the family's flavor the table's rows return; then `MockIVerifierAdapter::try_new(MockIVerifierAdapterConstructorParams { failure_mode, delivery_proof: deps.delivery_proof })`, exactly once, `failure_mode` the mode the `Mock` member of `params.concrete` carries, its success destructured by `let Ok(adapter) = …;` because its error arm is `Infallible`; then `deps.consumer.consume_verifier(ConsumeVerifierParams, ConsumeVerifierPayload { adapter })`, exactly once; the outcome is `Ok(CreateVerifierSuccessReturn { output })` holding the consumer's output.

## Ordering and invariants

- The match yielding the declaration, then the composition admission, then the version, then construction, then the consumer — the first refusal returns.
- `params.concrete` selects the concrete and carries its settings or failure mode; `params.verifier_address` carries the deployed delivery verifier's location beside the selection; `params.statement_version` admits; `payload` carries nothing and is not read.
- The deps' adapter borrows are copied into the constructor params, and the deps' `encoder` and `generate` declarations and the `admit_verifier_composition` handle serve the composition admission alone; the consumer is generic over `IVerifierAdapter` whose `DeliveryProof` is the caller's delivery proof adapter type, and never names the concrete.
- Adding a verifier concrete is its module, its variant in `VerifierConcrete`, its entry in `VerifierConcreteKind`, `VERIFIER_CONCRETES`, and the declared-selection builder, its variant in `CreateVerifierErrorReturn`, and its branch here — no consumer changes; the factory names no endpoint, address, curve, verifier form value, version value, chain member, encoding identifier, or contract suite.
