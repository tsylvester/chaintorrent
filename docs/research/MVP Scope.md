# MVP Scope

## Objective

Deliver a working install path for JavaScript dependencies that serves popular packages from a peer swarm, reuses across every project on a machine whatever that machine has already fetched, survives an upstream NPM outage for packages already ingested into the swarm, and exercises the full identity, entitlement, credential-delivery, encryption, and transfer lifecycle end to end.

**The individual developer is the adopting population**, and the benefits above are ordered accordingly. Cross-project reuse and swarm retrieval are what a developer at a terminal experiences; registry-outage survival — the benefit that matters most to CI and to enterprises — stays true without leading, because those populations adopt as a consequence of individual adoption rather than ahead of it.

Monetization is $0.00 throughout, with one deliberate exception described under Transaction Flow Proof, which exists to prove that a nonzero transaction settles rather than to earn anything.

This MVP validates **distribution and identity**. It deliberately does not validate willingness to pay or seeder compensation.

This document states the boundary of the work. Undetermined decisions are held in the To-Do list of [ChainTorrent MVP.md](workplans/current/ChainTorrent%20MVP.md).

Terminology follows [cryptography.md, Terminology](cryptography.md#terminology) — entitlement, handshake key, parameter set, master scalar, native credential, envelope key pair, envelope, header sidecar, piece-group key, variant seed, transfer sequencer, credential author — and the unqualified words "key" and "token" are not used for any of them. The adapter surfaces this document introduces are named on first use and used consistently thereafter: `ISwarmTransportAdapter`, `IPeerDiscoveryAdapter`, `ISeedHostAdapter`, `IPackageHostAdapter`, `IPublisherProofAdapter`, `IClaimVerifierAdapter`, and `IKeyCustodyAdapter`. They join the surfaces already defined in the specification — `ISignatureAdapter`, `IIdentityAdapter`, `IIngestSourceAdapter`, `IPairingAdapter`, `ICredentialKemAdapter` (the suite's deployment-encryption adapter), `IPayloadCipherAdapter`, `IKeyAgreementAdapter`, `IDeliveryProofAdapter`, `ISettlementAdapter`, and `IEntitlementStateAdapter`.

Sections in this document are referenced by name, never by position. The same rule governs [cryptography.md](cryptography.md), and cross-document references link to the named section rather than to a number that moves when anything is inserted.

# In Scope

## Adapter Composition and Capability Declaration

Protocol layers resolve adapters independently where the layer contract permits it. Independent resolution keeps a chain, a curve, a transport, or a custody implementation from becoming a protocol commitment — and it is also what makes it possible to resolve a pair that cannot compose. A custody implementation that cannot produce what a chain adapter verifies, a transport that cannot carry what a discovery adapter advertises, and a seed host that cannot satisfy a retention obligation are all resolvable and all broken.

**Each adapter interface declares its capabilities**, and capability is part of the interface rather than knowledge a consumer is expected to carry about particular implementations. An implementation states what it can do; a consumer resolves against the declaration, never against an implementation's name.

**Composition is checked at resolution time and fails closed.** An incompatible pair is refused at the point of resolution, before any operation is attempted, in the same posture as the manifest bounds validation of [cryptography.md, Cryptographic Primitives](cryptography.md#cryptographic-primitives): the ordering is the security property. A pair that would fail later is refused now, so no credential is exercised, no state traffic is spent, and no swarm activity is begun on a composition that was never going to resolve.

**The unit of cryptographic composition is an immutable deployment suite.** A deployment's authenticated hash-card fixes the pairing adapter, the credential-KEM adapter and the live parameter sets with their header sidecar roots, the payload-cipher adapter and piece-group size, the key-agreement adapter used for envelopes, the delivery-proof adapter, the KDF and hash-to-scalar mappings, the delivery-statement version, the attempt-rule parameters, the settlement tier, the content commitments, and the transport locators. A client may resolve only implementations declared compatible with every field, and a delivery-proof adapter only if it declares the chosen envelope algebra. Changing an incompatible cryptographic component requires a successor deployment; an interface boundary does not reinterpret existing ciphertext, and a successor body carries a header sidecar for every parameter set still live for the asset.

Per-layer resolution and the binding-not-matching rule of [cryptography.md, Cryptographic Primitives](cryptography.md#cryptographic-primitives) already dissolve most compositions that would otherwise conflict — two layers using different schemes need only be provably the same principal, not the same key. That is why incompatible pairs are rare rather than absent, and rare-and-unhandled is how a protocol acquires an undocumented compatibility matrix after the fact.

**The boundaries are drawn where they are because of what they are eventually meant to hold.** Chain, tokens, wallet, keystore, and seeder client are one class — third-party implementations now, first-party at maturity. Abstracting them is therefore not generic good practice applied uniformly; it is the specific list of components the protocol intends to supply itself, and each adapter is the seam along which someone else's implementation is later exchanged for the project's own. A layer that will never be replaced does not need an adapter. These will be.

## Swarm Transport and Peer Discovery

**Transport resolves through `ISwarmTransportAdapter`.** BitTorrent compatibility is an available adapter, not a protocol obligation. Pinning one transport while every other layer resolves an adapter would be a commitment the rest of this design does not make, and it forecloses transports whose native verification structure is the one the protocol already specifies.

* **BitTorrent is the compatibility implementation.** Unmodified clients participate in the swarm with no protocol integration, and the canonical record exposes the magnet link and BTIH that adapter contributes. The dual integrity structure that compatibility requires — legacy piece hashes alongside the BLAKE3/Bao tree over the same bytes — is a cost that adapter carries internally, not a property of the protocol.
* **BLAKE3-native transports are peer implementations, not future work.** A transport whose wire format is already Bao verified streaming carries no duplicate integrity structure at all.
* **A deployment may be multi-homed across transports simultaneously.** Ciphertext and plaintext roots are transport-independent by construction, so the same bytes served over two transports are one swarm object rather than two. Multi-homing is free rather than a compatibility burden, and no transport's absence invalidates a deployment.

**Peer discovery resolves through `IPeerDiscoveryAdapter`, with multiple adapters active concurrently.** Results are unioned and deduplicated, and no adapter is authoritative — DHT, tracker, PEX, local discovery, and the on-chain seeder map are peers of one another. A participant running none of them can still be served by a locator carried in the canonical record; a participant running all of them is not required to trust any one.

**Seeder maps are safe to publish, and that is a property of the design rather than a concession.** Seeder agnosticism ([cryptography.md, Seeder Agnosticism](cryptography.md#seeder-agnosticism)) means possession of encrypted pieces confers no access, so seeding an object implies nothing whatever about holding an entitlement to it. A public seeder registry is therefore strictly less disclosive than the entitlement ledger the protocol already publishes, and it is the one part of the network graph that can be published without adding to the exposure recorded in [cryptography.md, Dependency Graph Privacy](cryptography.md#dependency-graph-privacy).

## Seed Hosting and the Ciphertext Store

**Seeding is persistent and decoupled from any session.** A seeder that stops when an editor closes is not a seeder. The seed host runs independently of whatever client is using it, and the CLI, the editor extension, and any other consumer attach to it rather than contain it.

**Seed hosting resolves through `ISeedHostAdapter`**, with two MVP implementations:

* **Own daemon** — a machine-level service holding the swarm client, addressed over local IPC, single-instance per machine.
* **Delegation to an existing BitTorrent client** — driving a client the user already runs through its own API. Existing clients have already solved persistence, resume after crash, bandwidth scheduling, port mapping, and disk management, and their download directory is already a ciphertext store. This is what obligate BitTorrent compatibility was actually buying, and it is available as an adapter without being imposed as a requirement.

**The ciphertext store is an obligation of `ISeedHostAdapter`, not a component of the client.** Under delegation the store is a directory this protocol does not own, with a layout, naming scheme, and retention behavior it does not control, so the store is specified as a contract rather than as a filesystem structure. The adapter answers whether an object is held and served, takes custody of an object, releases one, reports capacity and usage, and enumerates what it believes it is serving.

* **The store is keyed on the ciphertext root, never on a transport identifier.** A multi-homed deployment must share one copy of the bytes across transports rather than storing one copy per transport, and a transport identifier cannot express that. The adapter owns the translation between the ciphertext root and whatever identifiers its implementation uses internally.
* **A delegated store's accounting is verified, not trusted.** The client cannot rely on an external application's report of what it holds. Verification is a BLAKE3/Bao authentication path over a random Bao chunk against the ciphertext root — the verification structure already exists, so this requires no additional cryptography.

**Two stores, two lifecycles.** The ciphertext store is the seeding substrate and is owned by the seed host. The plaintext CAS is the local reuse cache and is owned by the client. They serve different purposes, are sized independently, and are governed by different retention rules — a participant seeding two hundred gigabytes while caching five gigabytes of plaintext is a coherent configuration.

**The seeding archive is the user's, and it is visible.** What an identity seeds — objects, sidecars, sizes, obligated versus voluntary holdings — is exposed through the CLI, the desktop application, and the extension as the user's contribution to the swarm, in the way a torrent client shows its library; it is not a hidden system cache. The plaintext CAS stays private.

**The store interface distinguishes objects held under obligation from objects held voluntarily**, from the first implementation, even though the MVP enforces no obligation. Retention duty is assigned by the mechanism described under Retention Obligation below, which requires an identity and stake layer the MVP does not have. Marking the distinction now means enforcement is introduced later rather than retrofitted into a store that never recorded why it held anything.

## Package Manager Integration

**Package managers are extended into the swarm, not replaced.** npm, pnpm, yarn, and bun resolve dependency graphs correctly — including semver resolution, peer dependencies, overrides, workspaces, and lockfile semantics — and reimplementing that would duplicate solved work unrelated to swarm distribution or compensation. What this protocol replaces is not the package manager but the obligate distribution path underneath it.

**Package manager integration resolves through `IPackageHostAdapter`**, which serves an ecosystem's own read protocol from protocol-held content. The npm registry protocol is the MVP implementation, and it is not the definition — the PyPI simple index ([PEP 503](https://peps.python.org/pep-0503/) / [PEP 691](https://peps.python.org/pep-0691/)), the Cargo sparse index, and the Go module proxy protocol are peer implementations behind the same interface. Each maps its ecosystem's coordinates onto the canonical identity hash and serves artifacts from the local CAS.

**The CLI is the consent and control surface.** Redirecting a package manager's registry is an act a user performs deliberately and can see and reverse, never something that happens quietly on their behalf — a toolchain silently rerouted is indistinguishable from a compromised one, and a protocol asking for trust cannot begin by behaving like the thing it warns about. The CLI owns opting in, reporting state, and controlling the seed host. It is not a second client implementation and it does not resolve dependencies.

**Local availability is separated from local installation.** `node_modules` is disposable and re-derivable; the CAS is the durable artifact, held in both forms. Deleting and rebuilding a project's dependency tree touches neither the network nor the ledger, because the plaintext is already local and retained plaintext is outside the authorization boundary ([cryptography.md, Core Philosophy](cryptography.md#core-philosophy)). Two projects on one machine sharing a dependency fetch it once. Only an artifact absent from the CAS requires a decryption attempt.

**Resolution serves plaintext from whichever source delivers it within the declared budget.** The local plaintext CAS first; then local or swarm ciphertext when the identity already holds a credential, since an attempt is then a state read and a local decryption; then the ingest source when it is available. A grant is a chain transaction, so an identity without a credential that waited for one would see an install slower than npm even with a holder online, and the ingest source serves it instead. The encrypted swarm path serves a first install only when the ingest source is unavailable: the daemon waits a bounded time for a grant and then fails with an actionable result that leaves the request pending and acquisition running in the background, so a retry succeeds the moment a holder appears. Every install is identical to npm or better, never worse.

**Two operations run in the install path and must not be conflated.** **Entitlement acquisition** inspects the wallet and skips targets the identity already holds, because those need not be acquired again; for everything else it registers a request and runs in the background, as the next section states. **Per-attempt authorization** is a fresh state view before every piece-group key derivation and is never skipped, presumed, or cached beyond the deployment's freshness bound.

**A first run ends in independence.** The identity's first install of a dependency closure leaves the machine holding, for every asset in it, the plaintext, the deployment's ciphertext and sidecar, and a credential, so that every later action against the same closure needs neither the registry nor any other participant. Two rules produce that outcome beyond the resolution rule above. *A grant request is registered for every asset the ledger knows that the identity holds no entitlement to, whichever source served.* It is registered before or alongside the upstream fetch, on chain, batched per install into one sponsored operation, queued durably behind the identity's own binding and envelope-key registration and while the chain, the relayer, or its budget is unavailable, and it is fulfillable while the requester is offline, because the credential is encrypted to registered envelope keys and the envelope is recovered from chain history; the daemon watches for mints to its identity and picks up a grant fulfilled in its absence on its next run. *The deployment's ciphertext and sidecar are fetched while the request is pending.* In the background, at low priority, under the bandwidth, metered, and battery settings and the ciphertext store's quota, pinned until the grant lands and seeded blindly meanwhile, so the machine is a seeder before it is a holder and a holder before it needs to be one.

The branches. An asset absent from the ledger has nothing to request and nothing to fetch: the daemon is its First Finder and authors the first grant to itself, and the loser of a registration race enters the pending-request state like any new identity. Upstream bytes for an asset the ledger knows are checked against the canonical record's plaintext root, and a mismatch marks that deployment unverifiable, withdraws the request against its set, and bootstraps a fresh escrow deployment from the verified bytes. A grant arrives under whichever live set the granting holder has, so after it lands the daemon confirms it holds a deployment carrying that set and fetches one if the prefetched copy is under another. An explicit-publisher asset routes its request to the publisher's issuance policy, whose refusal is discretion and not an outage, and a priced asset is never acquired automatically, its request becoming a notice the user acts on or ignores. An asset already held gets no request. Rate limits admit a realistic closure at once, which batching makes cheap. None of the background work touches the foreground install, which waits only for the source that served it.

Independence is of the registry and of every other participant, and of everything while plaintext is retained, which is why retention defaults to unbounded; after plaintext eviction a decryption needs the ledger view as it always does. It is per asset version, so a changed lockfile reintroduces the dependency for the changed entries only. It is a visible state: each asset shows independent or pending, with the reason, on every control surface, and a project is independent when every asset in its lockfile is.

The costs are two, and both are consented rather than incurred silently. Disk and bandwidth roughly double on a first run, since the machine fetches and holds plaintext and ciphertext for every dependency, and the installer says so. Every request is a public record naming the identity and the asset, so a first run publishes the identity's dependency closure at once rather than as it is used; the auto-request and prefetch behaviors are consent items, and a cache-only mode, with no chain identity, no request, and no prefetch, exists for a user who wants only the local cache and the registry, which that user gets with no public footprint.

## Canonical Identity and As-Is Ingestion

* The **identity hash is deterministic**: `BLAKE3(packageName@version)`. This is what the Registry is keyed on, and it is what guarantees every node resolves the same asset to the same canonical record.
* The **ciphertext is not deterministic, by design**. A First Finder generates a cryptographically random master scalar and random capsule randomness. An explicit publisher may instead derive both from its secret hierarchy, the capsule randomness domain-separated by a registry-assigned, globally unique, non-reusable `deployment_id` and the piece-group index. Both strategies keep every key independent of plaintext and cryptographically distinct per deployment and per group, per the Anti-Derivability rule of [cryptography.md, Core Philosophy](cryptography.md#core-philosophy).
* Ingestion runs through the **`IIngestSourceAdapter`** ([cryptography.md, Ingest and Normalization](cryptography.md#phase-1-encryption-minting-and-seeding)). **NPM is the MVP implementation, not the definition** — pnpm, Bun, PyPI, crates.io, or a publisher's own release endpoint are peer implementations behind the same interface, and none of them is a special case.
* **MVP ingest eligibility is NPM availability.** The MVP performs no separate licence or use-rights classification: if the supported NPM source adapter can retrieve the version, it is assumed eligible for First Finder ingest.
* The First Finder **does not repackage or normalize** the artifact. It fetches the bytes exactly as served and hashes them as-is. For the NPM implementation that is the immutable `.tgz`. Normalization would break the source's own integrity attestation.
* The First Finder **must verify** the fetched artifact against the upstream release attestation before registering it, and record that attestation on-chain alongside the identity hash. For NPM the attestation is the registry signature over `name@version:integrity`, verified against the registry's published keys, together with the `integrity` sha512 it covers; a bare integrity value is not an attestation, since a registrant substituting bytes can publish a matching one. The on-chain field is source-dependent, not NPM-shaped. The registry verifies the signature again at registration through Base's P-256 precompile against a governance-updated table of source keys, so a registration without a genuine attestation for its declared digest is refused, and every conforming client verifies the bytes it decrypts against the attested digest before committing or serving them, so a genuine attestation attached to other bytes is refused at every client. This proves that the canonical bytes match the upstream release; it does not prove that the package is safe, non-malicious, or free of vulnerable dependencies.
* Two nodes ingesting the same unlisted package produce different ciphertext. This is resolved at the identity layer, not the payload layer: **State-Locked Escrow Registration** means the first transaction to land wins the asset record, and the losing node destroys its local ciphertext, header sidecar, master scalar, expanded cipher state, and buffered keystream, then resolves the winner's authenticated deployment descriptor and transport locator set. The lock is on the asset record and not on its deployment count: a later First Finder may register a further escrow deployment of the same asset under its own escrow set, which is what keeps the identity recoverable if a deployment's bytes fail the attestation check at every client that decrypts them. Such a deployment is dead and clients refuse it and resolve past it; the identity is never poisoned ([cryptography.md, State-Locked Escrow Registration](cryptography.md#phase-1-encryption-minting-and-seeding)).

## MVP Payload Cipher and Manifest Validation

**The MVP payload-cipher implementation is `AesCtrAdapter`: AES-256-CTR with a random 64-bit IV and a 64-bit block counter.** The IV is generated once per deployment and authenticated in its hash-card. The deployment is encrypted as one continuous byte stream under one IV, keyed per piece group with the key derived from that group's capsule; file boundaries do not restart the counter, and a second IV under any one key is forbidden. For piece index `i`, the starting block index is `(i × piece_size) / 16`. The maximum addressable extent is 2^68 bytes. The piece-group size is a suite parameter fixed per deployment from measurement; see the To-Do list.

Before entitlement acquisition or any decryption attempt, the client authenticates the deployment record and hash-card, resolves the immutable suite, validates all manifest bounds, and authenticates the header sidecar against its root. Piece size must be a power of two, at least 16 KiB, and a multiple of 16 bytes; total size, piece size, piece-group size, and piece count must agree; the highest block index must fit the cipher's declared extent; every requested piece index must be in range; and every capsule used must pass its well-formedness check. Any authentication, compatibility, or bounds failure halts before any credential is exercised.

## Native Credentials and Per-Attempt Authorization

* Every holder decrypts with its own **native credential**, delivered exactly once per ownership interval inside the settlement that creates the interval — the mint for interval zero, the sale for every later one — through the credential-delivery boundary of [cryptography.md, Cryptographic Primitives](cryptography.md#cryptographic-primitives). Nothing is requested from any party at read time.
* **Escrow deployments resolve the credential KEM at the asset identity scope**, so any current holder can author the credential for a newly minted zero-price entitlement from its own credential, and the conforming client serves pending grant requests for assets it holds automatically, as it seeds them, under the relayer's policy, including requests from identities that are offline at the time, since the credential is encrypted to the requester's registered envelope keys and recovered from chain history. The First Finder authors only the first grant, to itself; its permanent absence stops nothing. Explicit-publisher deployments resolve the entitlement scope, which is what gives a leaked credential its attribution.
* **Delivery is verified, not trusted.** The recipient registers an envelope key pair with proofs of possession under a wallet signature, once, reusable across entitlements. The credential author — the issuer at mint, the seller at sale — encrypts the credential to those keys through `IKeyAgreementAdapter` (`PairingElGamalAdapter`) and posts the envelope with a delivery proof from `IDeliveryProofAdapter` (`SchnorrFsDeliveryProofAdapter`). The contract verifies the proof through the pairing adapter's precompile interface and, in the same transaction, advances the interval counter, records the recipient's keys and the envelope digest, emits the envelope, transfers the entitlement, and releases payment. The proof's statement binds asset, parameter-set digest, exact entitlement, both interval counters, purpose, both parties, all four envelope keys, both envelopes, and an expiry; omitted fields are a hard failure.
* **Before every attempt** — every derivation of a piece-group key from a capsule — the client holds a state view at the deployment's declared settlement tier or above, no older than `τ_soft`, read through `IEntitlementStateAdapter.evaluateAuthorization(context)` over its `AttemptContext`: asset, deployment, exact entitlement, identity and bound handshake key, the interval index its credential was issued for, and the view's settlement reference. Results are `AUTHORIZED`, `PENDING_SETTLEMENT`, or `DENIED`; pending attempts wait or retry, denied attempts halt, and the paginated batch form preserves the per-context bindings. The client's session proves control of the handshake key, renewed every `τ_wallet`. An entitlement held for years authorizes nothing until a current view covers the attempt.
* Settlement tier is declared per deployment. Public First Finder/NPM deployments use `INCLUDED`, because their entitlement price is $0.00 and their plaintext is already publicly available. The priced explicit-publisher deployment used by Transaction Flow Proof declares and justifies its own tier rather than inheriting that default. Reads gate at the declared tier; destruction waits for `HARD`.
* **The persistent credential is stored; the decrypted one is not.** The envelope key pair, the envelope, and the interval index are held by `IKeyCustodyAdapter`, because they are the holder's transfer witness. The decrypted credential, piece-group keys, expanded cipher state, and buffered keystream are memory-only. On observing a transfer out at the declared tier the client stops attempts; when it reaches `HARD` the client destroys everything decrypt-capable. A lost envelope is recovered from chain history; lost envelope secrets end the ability to transfer, which is the holder's liability as with any key.
* `τ_soft`, `τ_wallet`, and the piece-group size are MVP configuration with published values; their selection is held in the To-Do list and is informed by the cost instrumentation below. No window ceiling or volume cap exists; any such limit is conforming-client policy.
* The credential is distinct per interval by construction and a leaked one names its entitlement, but a modified client can retain or redistribute its decrypted credential or the piece-group keys: the protocol claims bounded operation for the conforming reference client, not hostile DRM ([cryptography.md, Modified Clients](cryptography.md#modified-clients-the-honesty-assumption)).
* The credential construction is replaceable only by a suite compatible with the immutable deployment suite, introduced as a successor deployment whose body carries a header sidecar for every live parameter set. An adapter boundary alone does not reinterpret existing ciphertext.

## Retention Obligation

**Participation is an obligation of holding an identity, scoped per identity and never per device.** Sybil resistance is then inherent in the protocol rather than an overlay some other layer has to manage: one identity is one participant regardless of how many machines it runs, and running more devices buys no additional weight. Deliberate fragmentation of one operator into many identities is a distinct problem and is deferred rather than answered here.

**Retention of swarm ciphertext and header sidecars is that obligation's content.** It is assigned by random rotation over the participant set and audited on one surface. Three tiers, with different rules:

* **Obligated** — assigned by the protocol, held until reassignment, not selected by the participant and not evicted at the participant's discretion.
* **Self-interested** — the participant's own dependency closure, held because they use it, governed by nothing but their own choice.
* **Discretionary** — capacity offered above the floor, which is where compensation attaches once it exists.

**Replication is a construction rather than a hope.** Assigning each deployment to a defined number of identities produces that replication factor directly, instead of leaving aggregate resilience to emerge from voluntary contribution.

**The obligation is attested and audited, not enforced.** A delegated seed host cannot be compelled — a user can delete an object out of a client this protocol does not control — so non-compliance is made visible and costly rather than impossible, which is the same posture as [cryptography.md, Modified Clients](cryptography.md#modified-clients-the-honesty-assumption). The audit is a challenge asking an identity to produce a BLAKE3/Bao authentication path for a random chunk of a deployment it is obligated to hold. The verification structure already exists, so proving retention introduces no new cryptography.

**No committee holds any content secret.** There is no threshold custody, no resharing, and no provisioning membership to bootstrap: the only secret-bearing parties are credential authors acting once at mint, grant, or sale, and the First Finder holding the escrow master scalar for an optional handover. The MVP exercises discovery, seeding, leeching, entitlement acquisition and transfer with verified credential delivery, and local decryption end to end. Stake-conditioned/Sybil-resistant selection, retention assignment and penalties, rotation policy, replication factor, retention floor, and audit challenge frequency remain unenforced or unset and are held in the To-Do list.

## Local Content Addressable Storage

* Single global cache directory storing decrypted packages by content hash.
* Package managers extract from the served tarball into each project; nothing links into the CAS, and reuse is at the tarball.
* Plaintext in the CAS **persists by design and is outside the authorization boundary**. This is the retained-plaintext commitment of [cryptography.md, Core Philosophy](cryptography.md#core-philosophy), not a gap: a developer who installed a package keeps it and uses it with any toolchain.
* This store holds plaintext only. The ciphertext the participant seeds is held separately, under the seed host adapter, and the two are sized and retained independently.
* **Retention here is the user's decision, not the protocol's.** It is their disk. The client defaults to unbounded and exposes a quota; where a quota forces eviction, artifacts a live project resolved are pinned, and the client warns before evicting anything the identity could not re-authorize. Eviction is not an ordinary cache miss — re-materializing plaintext requires a fresh decryption attempt under a current state view, which fails if the entitlement has since transferred, so silent eviction can destroy access the user reasonably believed was permanent.

## Entitlement Ledger and Escrow Contract

Deployed on Base, an Ethereum L2 on the OP Stack. The ecosystem is Ethereum because ERC-721 entitlements and Solidity contracts are its native objects; the network is Base because both pairing precompile sets are live there since the Isthmus upgrade, L2 execution is cheap with the L1 data-posting fee as the dominant and measurable cost, and ERC-4337 bundlers and paymasters exist. Base Sepolia is the test network the validation harness deploys to. The pairing curve follows Ethereum's standards: BLS12-381 through EIP-2537 as the primary verifier form, with BN254 through EIP-196 and EIP-197 retained as the second. Settlement tiers map to sequencer inclusion, the safe head posted to L1, L1-finalized L2 state, and fault-proof resolution; the sequencer is a write-path dependency only. Ethereum mainnet is a later chain adapter, and migration of entitlements between chain adapters is unspecified and held in the To-Do list. First Finder entitlements are priced at $0.00; the explicit-publisher dogfood asset under Transaction Flow Proof is the sole nonzero-price exception.

* The asset record registers the package identity hash, upstream attestation, publisher or escrow authority, publisher proof class, entitlement adapter, issuance authority, the parameter sets marked live for the asset, and every live deployment. Each deployment carries an authenticated hash-card containing at least the registry-assigned deployment identity; immutable suite and version; payload cipher, IV, piece geometry, piece-group size, and total extent; one header sidecar root and locator per live parameter set; delivery-statement version, attempt-rule parameters, and settlement tier; ciphertext root; plaintext-root disclosure mode and value or explicit absence; and the transport locator set.
* **All three content roots are registered, not just a transport locator, and the plaintext root is registered in Public disclosure mode** ([cryptography.md, Cryptographic Primitives](cryptography.md#cryptographic-primitives)). Provenance and independent verifiability are the point of the package path, and NPM plaintext is openly distributed regardless, so there is nothing to mask. The ciphertext root establishes what the swarm carries; the sidecar root establishes which capsules a credential may be exercised against; the plaintext root establishes what a correct decryption must produce. Without it the `Verify plaintext root` step of the execution trace has nothing to verify against, and a client holding an incorrect credential produces garbage that passes every other check the protocol performs — see [cryptography.md, Cryptographic Primitives — Content Commitments](cryptography.md#cryptographic-primitives).
* **Per-entitlement delivery state.** For each entitlement the contract holds the interval counter, the current holder's registered envelope keys, and the current envelope's digest; the envelope and delivery proof themselves are calldata and an event. A transfer supplies the previous envelope in calldata, which the contract checks against the stored digest before verifying the transfer proof, so the entitlement's envelope history is the delegation chain the ledger authenticates. For an escrow deployment a grant's proof is verified against the author's own current envelope under the same parameter set, and the result is recorded as interval zero of the newly minted entitlement. Identity-element keys are rejected at registration and a mint whose identity element is trivial is refused.
* **Abuse controls.** Payment locks carry a short, published expiry, so a seller who never delivers ties up a buyer's funds only briefly; a listing bond is an optional market-design addition. Zero-price grants and relayer-paid mints are admitted under a relayer policy that bounds exposure globally, a per-window expenditure budget and a maximum sponsored liability, with per-identity limits as one layer, because each verifies a proof on-chain, an unmetered path converts the grant pool into gas, and identities are free to create, so per-identity limits alone bound nothing; exhaustion is an explicit failure and never a false authorization. The claim verifier's attestation key is registered on-chain with rotation and revocation, since its compromise would hand publisher authority over escrowed assets to an attacker. The per-attempt state view is a quorum, two of three configured nodes agreeing at a common reference within the freshness bound, so one censoring, unreachable, or stale node cannot deny reads, while divergent state at one reference and a view older than `τ_soft` fail closed.
* **Parameter sets are registered per asset and marked live or retired.** The escrow set is registered at bootstrap and the claimant's set at claim; a set is retired only when no entitlement issued under it remains live. A deployment record is accepted only if it carries a sidecar for every set live at registration; a record that omits one is rejected as incompatible. A holder under a retired-bound set may request a replacement credential under a live set, which the issuing authority mints for the same entitlement in one settlement that supersedes the old credential.
* **Delivery proofs are verified through the chain's pairing precompiles**, on the curve `IPairingAdapter` resolves for the launch chain — BN254 everywhere, BLS12-381 where its precompiles are deployed. The verifier's on-chain form follows the adapter's declared capability: a batched pairing-product check where only first-group arithmetic exists, plain source-group arithmetic where second-group arithmetic does.
* **Transport locators are a set, contributed by whichever transport adapters serve the deployment**, rather than a single transport-shaped field. A BitTorrent-served deployment contributes its magnet link and BTIH; a BLAKE3-native transport contributes its own address; a multi-homed deployment carries both and remains one object.
* Mints asset-bound entitlements to requesting identities as transferable bearer assets whose price is a contract parameter. The MVP implementation is an ERC-721 non-fungible token, so minting, holding, and transfer are ordinary operations with well-understood tooling; the protocol term remains "entitlement" and the token standard is the implementation, not the definition. An entitlement authorizes every live deployment of the asset, and the verified publisher may issue additional entitlements without a protocol-imposed supply ceiling.
* **Entitlement records are public, and that is a security and economic benefit for public dependencies.** The dependency inventory makes applications using known-vulnerable versions visible and creates pressure to update or remove them. It also makes paid distributions' consumption of open-source packages visible, strengthening the incentive to support the projects whose work they monetize. Private or internal content is a different case and no MVP ingest adapter targets it.
* Exposes `evaluateAuthorization(context)` and a semantics-preserving `evaluateAuthorizationBatch(contexts)` view through `IEntitlementStateAdapter`, read by the client at its own settlement reference. The complete context, three-state result, and client behavior are defined under Native Credentials and Per-Attempt Authorization.
* **Batch reads are paginated, with the ceiling advertised by the adapter rather than fixed here.** A dependency closure of a thousand packages is one paginated traversal, not a thousand round trips and not one request the recipient cannot accept. This mirrors the treatment authorization batching already receives in [cryptography.md, Phase 2](cryptography.md#phase-2-consumption-and-decryption), where batch size is negotiated against the implementation's limits because those limits are properties of the implementation.
* If a package is ingested via First Finder fallback, the contract creates an escrow record carrying source provenance, the upstream integrity attestation, and the escrow parameter set, and **no commitment to the maintainer's identity**. Email addresses are low-entropy and enumerable, so a bare hash would publish a permanently testable package-to-maintainer mapping — an on-chain disclosure the upstream source itself no longer makes, and the concern of [cryptography.md, Dependency Graph Privacy](cryptography.md#dependency-graph-privacy) arriving in a form the MVP actually ships. A salted commitment would avoid that disclosure but confers nothing the MVP's claim verifier can use, since the contract cannot check an email proof and the verifier already authenticates the claimant against upstream metadata at claim time, and it would make a lost salt a permanently unclaimable record; it is therefore omitted, and the claim set is established from upstream metadata at verification, per Escrow Claim.
* **Per-identity binding record.** The contract stores the bound handshake public key and its scheme on-chain — the fields on-chain logic must read — plus an anchor hash committing to the full DID Document, which resolves off-chain. Contracts cannot read an off-chain document without an oracle or a proof system, so the fields consulted during escrow claim verification and authorization checks are not among the anchored ones. See [cryptography.md, Binding Schema](cryptography.md#binding-schema).

## Explicit Publisher Path

A publisher who arrives before a First Finder registers their own asset directly, without an escrow record ever existing.

**This is the First Finder pipeline with three substitutions, not a second implementation.** Ingest, hashing, encryption, manifest construction, registration, and seeding are identical. What differs:

* The parameter set's master scalar and the capsule randomness derive from the publisher's own hierarchy — `seed_phrase → publisher_root → asset_root`, then the master scalar and identity bases per asset and the capsule randomness per registry-assigned, globally unique, non-reusable `deployment_id` and piece group, per [cryptography.md, Deployment Cryptographic Setup](cryptography.md#phase-1-encryption-minting-and-seeding) — rather than being randomly generated. Publisher authority rotation is separate from the stable derivation seed and does not version ciphertext.
* A Publisher Authority adapter is bound instead of an Escrow Identity adapter.
* No escrow record is created and no maintainer commitment is stored.

**Publisher identity proof resolves through `IPublisherProofAdapter` behind `IIdentityAdapter`, ordered by proof strength and resolved per package.** The strongest proof available *for that specific package* is used, and a weaker one is accepted only where the stronger does not apply:

| Priority | Proof | Applies to |
| --- | --- | --- |
| First | NPM provenance attestation (Sigstore bundle) verified, repository extracted, repository control proven by GitHub OAuth | packages published with provenance |
| Second | NPM maintainer OAuth, confirming the claimant is a listed maintainer | any package with a listed maintainer |
| Framed, not implemented | DNSSEC or DNS TXT proof binding a domain to the publisher identity | generic content; also the entry point for publishing website versions into the swarm |

**Swarm-native publication.** Publishing a package through this path also ingests its dependency closure: each dependency absent from the swarm is bootstrapped as First Finder and each present one is verified, so the package and everything it needs are in the swarm at publication. The MVP publishes ChainTorrent itself this way, which exercises the explicit-publisher path for the deployment and the First Finder path for its dependencies in one act.

**The proof class is recorded on-chain per record.** Governance in this protocol is advisory metadata parsed against a local trust set ([cryptography.md, Content Governance](cryptography.md#deprecation-advisory-flags-and-content-governance)), so a consumer able to see that a publisher was verified cryptographically rather than by maintainer email has information they can act on locally. Recording it also stops the weaker fallback from silently laundering into the same apparent authority as the stronger proof.

## Escrow Claim

**Claims are scoped per package *and* per version.** Ownership can differ between versions of one package — a maintainer publishes, the package becomes popular, and the next version is published under a corporate account — so records stay per-`(package, version)` and no claim locks a package name to one owner. Anything else would contradict transferable ownership, which is a founding premise of the protocol rather than a detail of the escrow path.

**A claim applies to a proof-derived set, not to a set the claimant chooses.** The verifier enumerates which records the presented proof actually covers at the moment of verification, commits to that set, and the contract applies one transition across the whole set in a single transaction. A maintainer of ninety versions makes one claim. A package whose later versions moved to a different owner yields two claims under two proofs over two disjoint sets, with no conflict and no adjudication. Different proof classes cover different and potentially non-contiguous version ranges over the same package name, and each claimed record carries the proof class that backed it.

**The claim is bound to the claimant's chain identity.** A proof generated for one address reverts if executed by or directed to another, per [cryptography.md, Escrow Claim Front-Running](cryptography.md#escrow-claim-front-running--identity-proof-binding), which is what prevents an intercepted verification proof from being front-run.

**Claim verification resolves through `IClaimVerifierAdapter` behind `IIdentityAdapter`.** The MVP implementation is an attestor: the verifier authenticates the claimant off-chain, then signs a voucher over the committed claim set, the claimant's address, and an expiry, using a key registered on-chain. A ZK-Email construction, a DNSSEC oracle, or any other verifier is a peer implementation behind the same interface and requires no contract change.

**No maintainer commitment is stored on chain, and no salt custodian exists.** The escrow record once carried a salted commitment to the maintainer's email, with the salt held by the provisioning layer, which no longer exists. The commitment's benefit is realized only if something checks a claim against it: the contract cannot, because it cannot verify an email proof; the claim verifier can, but it already authenticates the claimant against upstream metadata, so a compromised verifier could ignore the commitment and an honest one gains nothing from it; and checking it on chain would require revealing the email and salt, publishing what the salt hides. A snapshot of who maintained a package at ingest also conflicts with claims being per version and proof-derived at verification time. The verifier therefore establishes the claim set from upstream metadata at verification, which publishes no maintainer linkage and leaves nothing to lose. A ZK-Email verifier, a V2 peer implementation, can prove a DKIM-signed email matches a commitment without revealing it and may compute its own commitment at claim time without a custodian; a commitment is reopened only with such a verifier. The claim-set mechanism above is unchanged.

**A claimant receives complete protocol-level ownership, identical to an original explicit publisher.** Any difference in publishing authority, issuance control, administrative control, or standing to supersede between a claimed record and a directly published one is a defect. The expected difference is cryptographic history: the existing First Finder deployment retains its escrow parameter set, and later bodies carry a header sidecar for that set while escrow-era entitlements remain live.

**Escrow custody and custodial authority are distinct, and a claim never waits on the custodian.** The First Finder retains the escrow master scalar as custodian, issues credentials only against grants the escrow contract authorizes, and is contacted by nobody to read or transfer. On a successful claim the claimant registers its own parameter set as live for the asset and controls all future issuance under it; if the First Finder is reachable it may additionally hand over the escrow master scalar, encrypted to the claimant's registered envelope keys with a proof of compatibility, after which it erases its copy — a convenience, never a dependency ([cryptography.md, Escrow Key Lineage Across a Claim](cryptography.md#escrow-key-lineage-across-a-claim)). The First Finder never owns the deployment, and a copy it keeps beyond handover can author decrypting credentials but no entitlements, which is plaintext-equivalent capability it had from the moment it encrypted the object. The claimant may issue successor deployments, each carrying a sidecar for every live set; existing and successor deployments may remain live, and their shared plaintext root proves they carry the same asset.

## Transaction Flow Proof

Entitlements are $0.00 everywhere the protocol ingests content it does not own. That is not a pricing preference but a consequence of Content Bootstrap Does Not Confer Publisher Rights ([cryptography.md, Invariant Requirements](cryptography.md#overview-and-invariant-requirements)): a First Finder cannot price an asset whose publisher has not arrived, because the proceeds would accrue to a party that owns nothing.

**The MVP nonetheless proves that a nonzero transaction settles**, because a transfer path never exercised above zero is a transfer path never exercised at all — the price parameter, the payment leg, and the ordering of settlement against authorization are all untested while every entitlement is free. The proof is confined to the one asset class where nonzero issuance is legitimate: **the packages the project publishes itself**. ChainTorrent publishing ChainTorrent is an explicit publisher pricing an asset it owns, so no escrow record exists, no maintainer is absent, and no grandfathering question arises. The same dogfooding that seeds the swarm with its first content supplies the only assets that may carry a price.

Two legs, both priced trivially above gas:

* **Primary issuance.** The project mints priced entitlements to its own packages through the explicit publisher path, and a consumer acquires one.
* **Secondary transfer.** A holder resells that entitlement to another identity, and the settlement boundary is asserted: the seller's transfer proof verifies on-chain and payment releases in the same transaction, the buyer decrypts once the settlement reaches the deployment's tier, and the seller's reference client destroys its credential when the transfer reaches `HARD`.

This is a test instrument, not a revenue path. Everything ingested through First Finder stays at $0.00, and general monetization stays deferred under Paid Monetization.

## Key Custody

**Key custody resolves through `IKeyCustodyAdapter`.** Where an identity's keys live is an implementation choice like every other in this protocol, and pinning one store would be the same misstep as pinning one chain or one curve.

**The MVP custody implementation remains an unresolved, blocking selection.** Existing browser password managers and platform authenticators are candidates only if their actual APIs satisfy the required capabilities; browser synchronization, exportability, or key agreement cannot be assumed. The MVP does not select a split browser/local construction merely because a browser can sign.

**The adapter declares its capabilities**, because implementations differ in ways consumers must resolve against rather than assume:

* whether it can hold a signing key;
* whether it can hold an envelope key pair — two key-agreement secrets in the pairing adapter's source groups, which open credential envelopes, persist for every ownership interval as the transfer witness, and are a distinct primitive from signing (see the Key Agreement Adapter in [cryptography.md, Cryptographic Primitives](cryptography.md#cryptographic-primitives));
* whether it can protect an externally held key without holding it;
* whether an identity it holds can span devices, which the per-identity scoping of retention participation requires;
* whether it supports recovery without silently changing the identity; and
* whether it can protect the stable publisher derivation seed separately from rotatable identity/authority keys.

**This constrains no other layer.** Per-layer signature resolution and the binding-not-matching rule of [cryptography.md, Cryptographic Primitives](cryptography.md#cryptographic-primitives) mean a custody implementation serving the handshake layer imposes nothing on the chain layer, which resolves its own adapter and is bound by attestation rather than by matching. A custody choice is not a chain requirement.

**External wallets and the default identity.** The default identity is a local key held by the custody adapter, because a browser wallet cannot be assumed for a daemon. External wallets connect through the EIP-1193 provider interface or WalletConnect and only sign; signatures over registrations and bindings are EIP-712 typed data; and the relayer is an ERC-4337 paymaster where the network supports it. Envelope keys are never wallet keys under any of these.

**Identity custody holds the persistent credential, never the decrypted one.** `IKeyCustodyAdapter` holds the identity's own material — handshake, chain, and envelope keys, plus the publisher derivation seed where one exists — and, per entitlement, the envelope and interval index from the settlement that delivered its credential. The decrypted credential, the piece-group keys, and every cipher context are memory-only and are destroyed when the interval ends. A publisher's or First Finder's master scalar is issuance material under the same custody adapter, and its loss is recovered by registering a new parameter set rather than by any recovery service.

A first-party keystore is a later implementation rather than a later refactor, and it arrives with the rest of its class — chain, tokens, wallet, and seeder client — as described under Adapter Composition and Capability Declaration.

## Gas Relayer and Dev Grant Pool

* A dead-simple backend relayer (or Paymaster) funded by a developer grant that signs free entitlement mint transactions on behalf of newly generated identities, so a first-run user is not blocked on acquiring gas before they can install anything.
* **The subsidy covers the free path, and does not promise to cover every path.** Paid acquisition requires the buyer to actually pay, which means holding funds, which is a step the relayer cannot remove and should not pretend to — the Transaction Flow Proof accepts that step for the small number of identities exercising it. Real value entering the system is the intended direction of travel and is waiting on the technical elements being proven, not on a commitment to permanent subsidy.
* **One binding attestation transaction per new identity.** At wallet creation the relayer pays for a single transaction registering the identity's handshake public key, signed by the chain identity. It runs once per identity, never per install, and is invisible to the user.
* **Grant requests and their fulfilment are sponsored and batched.** A first run registers one request per asset the identity does not hold, in one sponsored operation per install, and the relayer sponsors the holder's fulfilling grant as it sponsors any free mint. Per-identity limits admit a realistic dependency closure at once; the global budget bounds what any flood of identities can spend; exhaustion leaves requests queued locally and is reported truthfully.
* Per-attempt state reads are **not** chain transactions and do not pass through the relayer. They are view calls, so authorization adds read traffic rather than gas cost. Credential delivery at a free mint is part of the relayer-paid mint transaction, whose cost includes verifying a delivery proof through the chain's precompiles; that cost is instrumented below.
* This is acknowledged scaffolding: it is a centralized chokepoint inside a decentralization thesis, and it is an unmetered subsidy. It exists to remove first-run friction, and it is expected to be replaced.

## Project Seed Host and Site

A project-run website explains the protocol and runs a persistent seed host for the core packages and their dependency closure, so the swarm has a seed of the core from the first day and development is not hostage to whoever happens to be online. It may also host the relayer and an optional discovery endpoint. It is the first seeder, not a privileged one: no client depends on it, the protocol resolves without it, and build platforms are expected to supersede it as superseeders. Any API it exposes is a convenience a client may use and never a component a client must reach. It holds an entitlement, and so a credential, for every asset it seeds, because a seeder that holds only ciphertext can author no grant: bytes being available and a new user being able to obtain a credential are separate conditions, and the seed host's availability promise covers both for the core closure ([cryptography.md, Parameter-Set Registration](cryptography.md#phase-1-encryption-minting-and-seeding)).

**The site carries the education tier and nothing that requires an account.** It explains the protocol, links the two onboarding paths, and hosts a browser demonstration built from the same Rust crates the client is built from, compiled to WebAssembly and run against a sample deployment: real resolution order, real Bao verification, and real decapsulation of sample capsules under a sample credential, with no service on the read path. Seeding and the plaintext CAS do not run in a browser, and the demonstration says so. The installer's consent flow reserves a step for linking an installation to a website account, so that the account and remote-head tier under Website, Account, and Remote Head in Deferred to V2+ is a later feature rather than a redesign; in the MVP that step does nothing.

## Distribution and Client License

The software ships under a license that permits forking and modification but makes producing a non-conforming client a violation, so that the modified-client case is a legal problem for the modifier as well as an accepted edge. Each asset's record carries the rights-holder's content terms; for the project's own packages those terms obligate holding an entitlement for personal and commercial use and a license per copy sold or bundled into a product. A conformance clause makes the software license source-available rather than OSI-open, which is a deliberate choice recorded against [cryptography.md, Core Philosophy](cryptography.md#core-philosophy); it binds forks of this code, not a clean-room client written from the specification. The license text, the OSI question, and the record field for content terms are held in the To-Do list and require legal drafting.

## Test Facilities

The MVP ships unit, integration, and end-to-end test facilities, including the demonstration harness of the Application Requirements, and every requirement's proof class maps to one of them. A requirement without a facility that can prove it is not complete.

## Cost Instrumentation

* Record relayer gas spend and swarm bandwidth per install. Cost-per-install is the first real unit-economics datapoint the project can obtain, and it is nearly free to capture at this stage.
* Record **state-read volume and latency** per install, separately from gas. This is the empirical input to choosing `τ_soft`, and it is what shows whether reading at the declared tier is a noticeable fraction of install time.
* Record **cryptographic costs on the resolved pairing adapter**: capsule, envelope, and proof bytes; decapsulation time per piece group; proof generation and verification time; and on-chain verification gas for a mint and a transfer. These are the inputs to the piece-group size and to the curve choice, none of which may be asserted from formulas alone, and the validation implementation that produces them is the first cryptographic thing built.
* Record **CAS hit rate and cross-project reuse** — how often an install is served from local plaintext rather than fetched, and how many projects on one machine share a given artifact. This is the benefit the adopting population actually experiences, which makes it the MVP's headline adoption metric rather than a secondary statistic.
* Record **independence after first run**: for each asset in the closure, which source served it and why, whether a request was registered, when the grant landed and the ciphertext was held, and the fraction of the closure independent at the end of the run, then time to independence thereafter. This is the measure of the first-run outcome Package Manager Integration promises.
* **The latency budget is declared before the run, and the measurement population is the local developer.** Interactive install wall-clock is the binding constraint, because a developer at a terminal notices a doubled install where a pipeline does not, and because individual developers adopt first. State the fraction of install wall-clock that authorization may acceptably add *before* measuring, so the instrumentation can produce a failure rather than a number. The economic half of the protocol-overhead question — what a single-digit fee would have to cover — is not discoverable at this stage and carries no threshold.

## Signature Scheme

The MVP resolves signatures through the **`ISignatureAdapter`** abstraction defined in [cryptography.md, Cryptographic Primitives](cryptography.md#cryptographic-primitives), resolved per layer, and ships two implementations.

**`Ed25519Adapter` is the protocol's preferred scheme** and is used at the handshake and content-signing layers — the layers where signature volume actually lives. Ed25519 is faster, is highly resistant to side-channel attacks, and is the general preference for new protocols. Delivery proofs are not signatures of either layer: they are chain-layer artifacts under `IPairingAdapter`, whose curve the launch chain's precompiles dictate.

**`Secp256k1Adapter` is shipped for the chain layer**, because Ethereum is the launch ecosystem and an Ethereum account *is* a secp256k1 keypair, permitting no alternative there. That is a constraint the target imposes, not a protocol preference — the launch network is Base, and the scheme a chain layer uses follows from whichever chain adapter resolves. A non-EVM target ships its own signature adapter and changes nothing above the chain layer.

The two keys are bound rather than matched: the Ed25519 handshake public key is registered in the Registry once at wallet creation, signed by the chain identity, in a relayer-paid attestation that is thereafter verifiable by any party. Additional chains and additional layers are new adapters, not protocol changes. Which scheme a given layer can use is constrained by the resolved key custody implementation's declared capabilities, and an incompatible pair is refused at resolution time per Adapter Composition and Capability Declaration above.

## What the MVP Does and Does Not Exercise

Per-attempt authorization and local decryption are built in full, but JavaScript dependencies exercise them lightly. A package is decrypted once at install, its plaintext lands in the CAS, and it is used from there indefinitely without further decryption — so the attempt boundary is crossed rarely for this content class, and each crossing decapsulates only as many capsules as the package has piece groups. That is the expected behavior of install-once content under the retained-plaintext commitment, not a defect in the mechanism.

The consequence for the MVP is that the *mechanism* is validated while its *load profile* is not. Streaming and large-media content classes, which decrypt continuously and would feel the per-group pairing cost, will exercise it far harder. Cost instrumentation exists so that the MVP still produces a usable baseline and a measured piece-group size rather than none.

Credential delivery is exercised at every mint and every transfer, with the proof verified on-chain each time; that is where the cryptography is proven rather than at read time. The encrypted swarm path serves a first install only while the registry is unavailable, so the remote encrypted hit is exercised under an outage or under a harness configuration that disables the ingest source, and on the ordinary path per-attempt authorization is exercised by holders: at reinstall after plaintext eviction and on a second device. Stake-weighted selection, Sybil resistance, retention assignment, and audit consequences remain deferred, but content discovery, seeding, leeching, entitlement, verified delivery, and local decryption must function end to end.

**Entitlement transfer is exercised, and it is the hardest thing the MVP proves.** The settlement boundary — the seller's proof verified and payment released in one transaction, the buyer decrypting at the declared tier, the seller's client destroying at `HARD` — is the specification's most contested invariant and the one whose failure mode is silent, since a wrong answer looks like a working install from the outside. Transaction Flow Proof exercises it end to end while the entitlement graph is two identities, which is the only point at which it is cheap to assert. What is *not* exercised is a market: price discovery, resale volume, and any behavior that emerges from many holders trading remain entirely unobserved.

# Deferred to V2+, but Architecturally Protected

## Git Commit Wrapping

Wrapping `git commit` output as swarm objects.

* **Why cut:** Git introduces mutable DAGs, branch delta tracking, and merge conflict complexity. Packages are static, immutable tarballs. Master package distribution first; tackle Git after the package network is live.

## Active Email Bot for First Finder Escrow

* **Why cut:** Sending automated emails every time an un-registered package is ingested creates spam risks, domain reputation hurdles, and unnecessary backend state.
* **Architectural protection:** The escrow record carries source provenance and the upstream attestation and no maintainer commitment, per Entitlement Ledger and Escrow Contract in In Scope. When the maintainer eventually shows up, they authenticate through `IPublisherProofAdapter` and claim every escrowed record their proof covers in one transaction, with the claim set established from upstream metadata at verification time as Escrow Claim records; the claim-set mechanism is unchanged by the absence of an email bot, and a ZK-Email verifier can later add a commitment computed at claim without a custodian.

## Paid Monetization

General entitlement monetization beyond the narrowly scoped explicit-publisher dogfood transaction in Transaction Flow Proof.

* **Why cut:** Introducing token economics, pricing, or fiat-to-crypto rails introduces immense regulatory and implementation drag.
* **Architectural protection:** The contract treats entitlements as transferable bearer assets whose price is a parameter. Changing that parameter from `0` to `X` later requires zero client refactoring.
* **Publisher discretion is configuration, not per-request approval.** Minting is the publisher's discretionary act, and discretion is exercised as an issuance policy the publisher sets: available for sale or not, at what price, under what limits, and served automatically by the publisher's client under that policy as escrow grants are already served automatically by holders, so a purchase completes without a person present. Nothing precludes a publisher from configuring per-request approval instead, or from overriding the policy for an individual request; those are settings the publisher authority adapter declares as capabilities, versioned so later policies can be added without a protocol change. Automation changes nothing about the invariants: issuance remains the publisher's right and never an obligation, and no existing entitlement's use or transfer depends on it.

## Version Alignment Engine

Dependency tree warnings and multi-version bloat diagnostics.

* **Why cut:** Calculating and warning about multi-version package bloat adds UI/UX complexity, and dependency resolution belongs to the package manager rather than to this protocol.
* **Architectural protection:** The host adapter resolves exact hash matches; version alignment can be surfaced later as a diagnostic feature (`torrent audit`).

## Arbitrary Media and Streaming Engine

* **Why cut:** Video byte-range seeking requires a completely different client pipeline. Stay 100% focused on JS developer dependencies.

## Content Flagging and Deprecation Surface

* **Why cut:** The backlink metadata layer is not built in the MVP.
* **Architectural protection:** Canonical records are immutable, but *advisory* — see [cryptography.md, Content Governance](cryptography.md#deprecation-advisory-flags-and-content-governance). Deprecation, malware advisories, and unwanted-content flags are backlink metadata parsed against the client's trust set, not registry mutations. Framing the handler now costs nothing; implementing it can wait.
* **The object model is designed once, not per type.** Advisories, deprecations, stars, comment chains, ratings, and reactions are one append-only backlink construction carrying different payloads. This layer is therefore specified as that construction rather than as a set of features, and the reason it is cut from the MVP is that the construction is its cost — a single advisory type requires the whole spine, which is why it is not the cheap increment it appears to be.

## Per-Entitlement Variance and Forensic Attribution

* **Why cut:** Variant seeds, seed re-issuance on transfer, and collusion-resistant fingerprinting are meaningless while entitlements are $0.00 and content is permissively licensed. Seed authorship is itself unresolved ([cryptography.md, Variant Seed Authorship](cryptography.md#variant-seed-authorship)).
* **Architectural protection:** The MVP ships **native credentials only** ([cryptography.md, MVP Posture](cryptography.md#mvp-posture-native-credentials)) — content uniform across holders, each holder's credential distinct. Enabling variance later adds a variant root to the entitlement record and confidential auxiliary material to the credential envelope delivered at mint and transfer, and requires no change to the identity, registry, or entitlement layers. Because the variant seed is committed to by the entitlement rather than stored in the swarm, and because variance is an overlay applied after verification, it does not alter the ciphertext the MVP distributes and introduces no additional swarm object to store, serve, or locate. See [cryptography.md, The Variant Seed Lives in the Entitlement](cryptography.md#the-variant-seed-lives-in-the-entitlement).

## Recipient-Bound Decryption Credentials

* **Moved into scope.** Native credentials bound to the exact entitlement and ownership interval are what the MVP ships, under Native Credentials and Per-Attempt Authorization; the interval, not a window within it, is the unit. What stays out of scope is interval-level attribution of leaked material, which a rerandomizable credential cannot supply and which per-entitlement variance addresses at the plaintext layer instead.

## Composable Container Objects

* **Why cut:** Sharing pieces between a collection and its members needs a container object type whose hash-card lists member deployments by their own roots, in the manner of BitTorrent v2's per-file trees, so that seeding the container seeds its constituents; the object model is not designed yet, and BitTorrent v2 is the reference to draw from when it is.
* **Architectural protection:** Byte-embedding nesting is already permitted and shares nothing; reference nesting adds an object type and touches neither commitments, entitlements, nor delivery.

## Partial Encryption and Duplicate Storage

* **Why cut:** Selectively encrypting only high-value regions requires a canonical segmentation policy and complicates random access and verification. The MVP encrypts the entire artifact and accepts the resulting plaintext-CAS plus ciphertext-store duplication.
* **Architectural protection:** Payload structure is opaque to the transport and entitlement layers. A later suite can declare an authenticated partial-encryption map while preserving the same content commitments and authorization surface.

## Consensus-Native Provisioning

* **Moved into scope, in a stronger form.** No provisioning intermediary exists: a credential is delivered once inside the settlement that records the entitlement, verified by a proof the contract checks, and every read is local against a state view. Consensus authenticates state and orders settlements; it holds no secret and computes no capability, which is what made the earlier framing of a consensus-native *provisioner* unreachable.

## Seeder Compensation

* **Why cut:** Rewarding seeding requires the token economics cut under Paid Monetization, and the Sybil-resistant stake that makes retention assignment enforceable is the same requirement.
* **Architectural protection:** Seeding is already the network's distribution mechanism and needs no structural change to become compensated. The retention tiers under Retention Obligation name discretionary capacity as the tier compensation attaches to, and the store interface already distinguishes obligated from voluntary holdings. Retention assignment and seeder compensation resolve together rather than separately, because both bottom out in Sybil-resistant stake over the same participant set.

## Website, Account, and Remote Head

A website account created with a familiar sign-in, a remote view of the user's local installation reachable from that account, and a hosted instance for users who do not want a local install. The pattern is the one media servers and torrent clients use: a platform-managed web head, a user-managed local instance, and a claim that joins them.

* **Why cut:** an account service, a rendezvous, a remote head, and a hosted instance are three or four new deployables against a delivery surface already wide, and the record that maps a familiar sign-in to an on-chain identity is the single deanonymizing transaction that [cryptography.md, Dependency Graph Privacy](cryptography.md#dependency-graph-privacy) warns retroactively unmasks an install history. Both are reasons to design the boundary now and build the tier later.
* **What a pre-install web account owns:** onboarding state, preferences, a roster of the identities and devices the user has linked, and optionally an end-to-end encrypted holder seed blob under a secret the user holds. It never owns an entitlement. Entitlements begin when a local cryptographic identity exists, because every credential is encrypted to registered envelope keys and an account has none.
* **The principal is the identity, never the account.** The identity is the registered envelope key pair and the bound handshake key. A sign-in provider authenticates a person to the account; it cannot be translated into a key, and deriving any key from an email address, a provider identifier, or a token is a protocol violation. An installation links to an account by a signed challenge from the identity's own keys proving possession, and the account-to-identity mapping is held only by the account service, is never written on chain or into the DID Document, and is optional: an identity with no account is fully functional and loses nothing.
* **Multi-device is one seed moving, not keys being re-registered.** The custody adapter may derive the holder's envelope secrets and handshake key from one holder seed through a domain-separated KDF, as the explicit-publisher hierarchy under [cryptography.md, Deployment Cryptographic Setup](cryptography.md#phase-1-encryption-minting-and-seeding) already does for parameter sets; this is an implementation choice within the Anti-Derivability rule, since the seed is random and no key derives from public material. Adding a device then moves one seed, by paired transfer over the local network, by an authenticator-wrapped export, or by the account's encrypted blob, and the custody adapter declares which it supports. Registering fresh envelope keys on a new device is not a link; it is a sale to oneself per entitlement, and the tier never does it silently. Not every device of an identity holds the seed. Device roles are capabilities the custody adapter declares, and the declaration is versioned so roles can be added or extended later without a protocol change: a **full** device holds the seed and every derived key; a **read-delegate** device holds only decrypted credentials, in memory, supplied by a full device over a secure channel under a delegation signed by the identity's bound handshake key, and can read but never transfer, which the specification already permits by separating the persistent credential from the decrypted one; a **signer-only** device holds the chain-signing and handshake keys for payments and approvals and no envelope material. A CI runner is a read-delegate of an always-on full device; a phone is a full or signer-only device. Local presence, wherever this section requires it, means presence at a device that holds the identity in a role that permits the operation, not presence at any particular machine, and it means an interactive confirmation through a surface the daemon owns, the desktop application's dialog or the platform's native prompt, which the CLI invokes rather than replaces. The confirmation exists because every process of the installing user is the same principal to the operating system: the daemon cannot tell a lifecycle script from the user, so it does not try; a script running as the user can request a package and nothing more, and every operation this section places under local presence completes only after a confirmation no IPC message can supply, which is the promise XA-02 makes and the only one a single-user desktop can keep.
* **The remote head is a view onto the local daemon, and the read path stays local.** The daemon dials a rendezvous with an outbound connection only, so no port is opened and the local IPC stays local under XA-02; browser and daemon communicate end to end under a key the daemon pins, so a compromised rendezvous can deny service but cannot read or forge; commands go to the daemon and signing and envelope material never leave it; remote capability is limited to status, the seeding archive, jobs, footprint, diagnostics, and repair, while transfer, key export, binding changes, and uninstall require local presence; and the consent trace records which surface authorized what. If the site is gone, installs and decryption are unaffected.
* **A hosted instance is a separate product mode.** It has a service on its read path and holds custody, so it cannot carry the local-independence claim and is declared as its own adapter with its own availability and custody promise, never as the default.
* **A sign-in provider is a Sybil-cost input, not a protocol rule.** Per-identity rate limits on free mints are cheap to evade because identities are free to create; an account backed by a provider is a cost the relayer's policy may consult. That is an adapter input under Gas Relayer and Dev Grant Pool, and intentional identity fragmentation stays deferred where the To-Do list holds it.
* **Architectural protection:** the installer's consent flow reserves the link step under Project Seed Host and Site; the custody adapter's declared capabilities under Key Custody already include multi-device and recovery, which is where seed sync is declared; the daemon's authenticated IPC under XA-02 is the surface a remote head would drive; and the browser demonstration is built from the client's own crates, so the education tier and the client never diverge.
