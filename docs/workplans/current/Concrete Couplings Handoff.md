# Concrete Couplings Handoff

## Topic

The harness-crypto architecture, and the workplans and planning documents that state it, bind code outside an adapter family to that family's concretes. This report hands the review and its correction scope to another agent.

## The governing requirement

Every concrete is reached through its family's factory, which constructs an adapter received as the family's interface, so the application is modular and composable. No concrete coupling is acceptable anywhere: production code, family interfaces, configuration admission, composition, tests, planning documents, or workplans.

The measure of success, as the user stated it: adding a new chain and verifier is accomplished by adding the adapters to the chain and verifier families, updating each factory, and adding that chain's and verifier's contracts under their own identities in the contracts space. Nothing else changes. The same holds for a pairing, an encoding, a contract generator, and every other family.

Adapters declare themselves in enough detail that the harness routes forms, fields, costs, and reports from declarations and never from knowledge of a concrete.

Incompatible combinations of chains, verifiers, contracts, and curves are determinate from declarations and are refused before anything is constructed against them.

## Decisions the user has made

- The harness runs a matrix over the pairing concretes, the target-group encoding identifiers, and the encodings. Each list defaults to its family's declared set when the configuration carries none; a configuration file or flag narrows it. Each cell runs as far as it can and reports its own outcome; no cell's refusal ends the run.
- The chain forms, the verifier, and the contract generator are single configured selections. They are not matrix axes.
- A delivery's cost is the verifier concrete's own type, reported through a description the verifier family owns. The measurement, the report, and the output render from that description and name no cost field.
- Every chain has a fee object in the abstract whose concrete form its adapter determines. The chain family describes a transaction's estimated fee, from the request its caller hands it, as the family's description, and the verifier's cost carries that description. The fee is an estimate: nothing is signed, sent, or settled against the incomplete implementation.
- The generate family is inside this correction, on the same terms as the verifier family.
- A chain's network values are configuration for the adapter that provides the chain, reached through that family's factory against a declaration. See the section on network values.
- Every problem class below is in scope in every workplan file. Nothing found is excluded.
- Each generated cell directory is named for the cell, one segment per matrix axis from the names the declarations supply. Foundry tests run once per directory. Deployment is once per distinct curve name.

## Problem: the chain's network values

The values are the endpoint, the gas price oracle, the chain identifier, the entitlement contract, and the precompile encodings.

Evidence. `harness-crypto/config` authors `apps/harness-crypto/harness.toml` with a `[network_profile]` table holding `verifier_endpoint`, `chain_identifier`, `entitlement_contract`, `precompile_encodings`, and `gas_price_oracle` as Base Sepolia literals, the oracle described as "the OP Stack predeploy `EvmVerifierSettings` names". `config/admit_statements` admits the chain identifier, the entitlement contract, and the gas price oracle. `harness-crypto/config` admits the endpoint. The dependency map's `harness-crypto/config/admit_statements` ownership list states the same.

Requirement. The values belong to the adapter that provides the chain. They are reached through that family's factory against a declaration that provides the adapter's configuration. No harness module holds or admits them as its own, and no consumer names the chain.

Requirement. The adapter's configuration is not hard-coded. The user sets each parameter to the extent that chain allows it to be configured. The declaration therefore states, for each parameter, whether the chain fixes it or permits it to be set, and the bounds within which it may be set; a value the chain fixes cannot be overridden, and a value it permits is taken from configuration with the adapter's default where none is supplied.

Requirement. The owner is authored once, complete, at its first consumer. The owner is `chain/base`, which with `chain/factory` and every ticket they need now precedes the harness's verifier client, its first consumer.

Delivered. The Chain Prerequisites Handoff mapped those tickets and placed their placeholder nodes; see "Delivered by the Chain Prerequisites Handoff".

Superseded. An earlier statement in the originating session placed the endpoint and oracle in the EVM verifier's own settings, the chain identifier and entitlement contract with the statements, and the precompile encodings with the pairing factory's params, to be moved when `chain/base` arrived. The user rejected that as build-part-now-and-redo-later. The verifier, the statements, and the pairing admission receive these values from the chain adapter.

Resolved, under `composition.md` on determined values, a value a received adapter fixes being read at the level that receives it and handed inward and never carried as configuration by a caller, and under `families.md`, "Reading a declaration before construction" and "A family's surface carries no concrete's model":

- The endpoint, the chain identifier, and the entitlement contract, which every chain member provides, are read from the constructed chain through the chain family's consumer surface. The harness receives the chain in a run consumer of `chain/factory`, `harness-crypto/run/chain_consumer`, inserted below, since only the run calls a factory and `chain/factory`'s composition admission needs the resolved forms.
- The verifier concrete reaches the deployed verifier at the endpoint of the chain adapter its factory hands it.
- The statements' chain identifier and entitlement contract are read by `harness-crypto/run/chain_consumer` and handed to `harness-crypto/run/admit_contexts`, so `CanonicalDeliveryContext` carries neither and no configuration admission admits either.
- The precompile encodings are stated in the chain member's declaration as the pairing family's values it works with, and the run reads them through `chain/lookup_chain_declaration` from the configured chain selection's identifier before calling `create_pairing`.
- The gas price oracle stays in Base's declaration and settings and reaches no family surface. The verifier's cost carries the chain family's estimated-fee description, which `chain/base` composes from its execution gas estimate and its L1 data fee read through the oracle.

## Problem: harness code outside a family that uses a concrete's own types

These are the bindings that force edits outside the adapter and factory when a concrete is added.

Verifier:

- `harness-crypto/config` admits "the verifier's endpoint text … through `EvmVerifierEndpoint::try_new`", its `HarnessConfiguration` carries `pub verifier_endpoint: EvmVerifierEndpoint`, and its `ConfigErrorReturn` carries `VerifierEndpoint(EvmVerifierEndpointTryNewErrorReturn)`.
- `config/admit_statements` admits `gas_price_oracle` into `AdmittedNetworkProfile`.
- `config/layers` declares the document keys for the endpoint and the oracle in its network profile table.
- The verifier module's `provides.rs` re-exports the concrete's `provides`, "the concrete's configuration surface", to every module of the app crate.

Generate:

- `config/admit_generate` builds "`GenerateConcrete::Solidity { settings }` … by an exhaustive `match`", reads `SOLIDITY_GENERATE_DECLARATION` directly, and calls the Solidity concrete's name, library, compiler-version, and license constructors.
- `harness-crypto/config`'s `harness.toml` holds "one table per kind of `SOLIDITY_GENERATE_DECLARATION`" and the Solidity compiler version, license, and library tables.
- `config/layers` declares the document tables those settings arrive in.

Requirement. A concrete's own settings are declared in the concrete's interface and carried in its variant of the family's selection (`composition.md`, "Configuration follows ownership"). The step that turns the document's values into that selection is owned by the family, since it must name each concrete; no configuration function, composition root, or consumer names a concrete's type, constant, or constructor. The document carries a concrete's settings in a table the selected concrete owns, so a further concrete adds no key to a shared table.

No other family has this defect in the harness nodes: the other families' selections carry no settings. The chain family's selection carries Base's settings and is admitted through `chain/admit_chain_selection`, which `harness-crypto/config/admit_selections` calls.

With the endpoint and the oracle gone to the chain and the deployment location to the verifier family's params, the verifier concrete's own settings hold only what it alone takes, if anything; its settings-document type, its guard, and the admission of its own settings are its node's, called by `harness-crypto/verifier/admit_verifier_selection`.

## Problem: missing admissions

Evidence. `VerifierDeclaration` holds `verifier_forms`, `statement_versions`, `adapter_version`, and `interface_version` and no chain forms requirement. `EvmVerifierErrorReturn::Fields` and `EvmVerifierTryNewErrorReturn::IdentityKind` are each described as a branch "no form the repository declares yields", so an incompatible forms concrete fails at the first call. `GenerateDeclaration` holds `kinds`, the versions, and `encoding_identifier` and no chain forms requirement.

Requirement. Each declaration states what it requires of the adapters it is composed with, and each factory refuses a mismatch before constructing anything, as `chain/create_chain_forms` admits the encoder by the encoding identifier the forms concrete requires. At minimum the verifier and generate declarations state the chain forms identifier they require and their factories admit against the resolved forms' declaration. The receiving agent enumerates every pairing of chain, verifier, generator, contract suite, and curve whose compatibility a declaration must make determinate, including the verifier's and generator's relation to the contract suite they target and the verifier's relation to the chain member whose adapter it is handed. `chain/admit_chain_composition` already admits the chain member against the resolved forms.

Requirement. Refusal precedes effort. The run's delivery proof consumer calls the generate factory, whose emission writes files, before the verifier factory. An incompatible verifier is therefore refused after files are written. A missing deployment record is a different case: it is a missing runtime input, and the planned first run writes its files and then refuses at the verifier stage naming the curve.
