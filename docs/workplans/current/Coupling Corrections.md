# Coupling Corrections

## Purpose

This document holds the scope and order of the corrections that remove five couplings from the specifications, the planning documents, and the workplan nodes. A coupling is a concrete form fixed at a point the architecture intends to be replaceable, with no adapter, declaration, or identifier between the concrete and the generic workflow that consumes it. The corrections change documents and workplan nodes. Implementation files follow from corrected nodes through the ordinary authoring path. The scope is complete when the completion check at the end of the order passes.

Each coupling below states where it is fixed and the position its correction establishes. The order section then states how the corrections run, and the layer sections state every document and node the corrections touch, with their disposition.

## Couplings and the positions their corrections establish

### Signature-scheme coupling

**Where it is fixed.** `ISignatureAdapter` declares `recoverSigner(message, signature) -> address` and `canonicalAddress(pubkey) -> address` (`cryptography.md`, Signatures; `system-architecture.md`, Interfaces; `dependency-map.md`, `signature/ed25519`). Key recovery is a property of ECDSA over secp256k1; Ed25519 and lattice signature schemes such as ML-DSA have none, and `address` is the EVM's twenty-byte form, so the concrete that authors the generic trait cannot implement it. The on-chain binding record stores `handshakeKey bytes32` and `scheme uint8` (`technical-requirements.md`, Database Schemas; `cryptography.md`, Binding Schema, "roughly two storage words"), a width that fits Ed25519 and no scheme with a larger public key. The identity account's signer set is keyed by `deviceKey address` (`technical-requirements.md`, `DeviceSigner`), which admits only keys whose signatures the account verifies by EVM signature recovery.

**Position.** The generic signature interface is signing and verification over a public-key type and a signature type the concrete supplies as associated types. Key recovery is a capability a concrete declares, never a method of the generic trait. Deriving an address from a key is the chain family's identity form, which `chain/evm_forms` already owns for the EVM suite. The family's declaration carries the scheme identifier, the public-key and signature lengths, and whether recovery is supported. On chain, the binding record carries the scheme identifier and a commitment to the handshake public key, with the key itself carried in calldata and in the anchored DID Document, so the stored width does not depend on the scheme. A device signer on the identity account is keyed by a scheme-tagged key identifier, and the account verifies a device's signature through the on-chain signature adapter the adapter registry binds for that scheme. Ed25519 and secp256k1 are the MVP concretes.

### Solidity coupling

**Where it is fixed.** The Application Requirements state "EVM contracts use Solidity because the target execution environment requires contract bytecode" (`MVP Application Requirements.md`, Implementation Language and Runtime Policy), and the tech stack lists Solidity as fixed; the execution environment requires bytecode, which several source languages produce. Contract suites are identified only by their virtual machine (`contracts/evm`, `contracts/<suite>`), so a second source language for the same machine has no identifier and no path. The harness's `generate` family has one concrete, named `evm`, whose rendering function emits Solidity library source with its license and pragma lines and whose vector-record library is read by Foundry (`dependency-map.md`, `harness-crypto/generate/evm/render`, `harness-crypto/generate/evm`). The Rust verifier client `harness-crypto/verifier/evm` authors `contracts/evm/src/IDeliveryVerifier.sol`, `contracts/evm/foundry.toml`, and `.github/workflows/contracts.yml`, and binds the contract through `sol!` over the Solidity source file (`dependency-map.md`; `tech-stack.md`, Next Steps; `ChainTorrent MVP 5.md`, `harness-crypto/verifier/evm`). The on-chain adapter registry binds the identity adapters, the signature adapters, the attestation verifier per source, and the entitlement token form, and does not bind the delivery verifier or the pairing library, which the registry contracts call directly (`technical-approach.md`; `system-architecture.md`; `dependency-map.md` and `milestones.md`, Adapter registry and factory, on chain), while `product-requirements.md` states that a further proof scheme is a further on-chain concrete.

**Position.** A contract suite's boundary with the client is its ABI, and a suite is identified by its virtual machine and its source language; the MVP suite is the EVM suite in Solidity under Foundry. Requirement text states that EVM contracts compile to EVM bytecode from the source language the suite declares, Solidity in the MVP. The delivery verifier's interface is a language-neutral ABI description the contract suite owns; the Rust verifier client binds to that description, keeps its name `verifier/evm` because it speaks the EVM ABI, and authors no contract source and no toolchain file. The Solidity interface, the Foundry configuration, and the Solidity continuous-integration definition are authored by the Solidity suite's own nodes. The harness's generator concrete is named and declared by the language it emits, and the vector files it writes stay ABI-encoded and language-neutral, so a further language is a further generator concrete. The adapter registry binds the delivery verifier per delivery-statement version and verifier form, constructor-injected and immutable once bound, beside the adapters it already binds, and the registry contracts reach the verifier only through that binding.

### Asset identity coupling

**Where it is fixed.** The canonical identity is `BLAKE3(packageName@version)` and the registry is keyed on it (`MVP Scope.md`, Canonical Identity and As-Is Ingestion; `cryptography.md`, The Hash-Card, Phase 1, and the publisher lineage; `MVP Application Requirements.md`, PR-02; `MVP Execution Trace.md`, `LEDGER_LOOKUP`; `dependency-map.md`, `domain/asset_identity` and `domain/asset_identity_hash`). The preimage names no ecosystem, so the same name and version in two registry ecosystems resolve to one registry key once a second ecosystem's adapters exist, which `MVP Scope.md` names as the next expansion.

**Position.** The canonical asset identity is the registry ecosystem, the package name, and the version, which is exactly what a package request carries. The ecosystem is the registry's, never the client's: npm, pnpm, yarn, and bun resolving against the npm registry produce one identity, and the method a user fetches by matters only to that method's own adapter. The package host declares the ecosystem whose protocol it answers in, and the ingest adapter for the same registry declares the same one. The identity hash is defined behavior, `BLAKE3(ecosystem ":" coordinates)`, where `ecosystem` is a token the specification fixes per registry ecosystem and that contains no `:`, and `coordinates` is that ecosystem's canonical coordinate string; for npm the token is `npm` and the coordinates are `name@version`. The hash is computed from the request before any record is read, so no record names its derivation, and it never changes, since canonical records are immutable: a new encryption of the same version is a new deployment under the same identity, and a new version is a new identity. The derivation is therefore fixed by the specification and is not a seam.

### Suite-shaped on-chain state

**Where it is fixed.** The registry's storage and API carry the MVP suite's algebra in typed fields: `ParameterSet` holds `g1, u0, u1` first-group points and `g2, hpub` second-group points, `EnvelopeKeys` holds a first-group `pk1` and a second-group `pk2`, `Entitlement` holds a first-group `identityElement`, and `registerEnvelopeKeys(pk1, pk2, pop1, pop2, walletSig)` takes them by shape (`technical-requirements.md`, APIs and Database Schemas). `Deployment` holds `iv bytes8`, which fits the 64-bit IV of AES-CTR and not the 192-bit nonce of the `XChaCha20Adapter` that `cryptography.md` lists as a candidate, and fixed `bytes32` roots. `Deployment` carries no commitment-scheme identifier, although `cryptography.md` and `product-requirements.md` state that the hash-card carries one. A successor suite, the documented path for any cryptographic change, would require new contract storage.

**Position.** Suite-specific public material, parameter sets, envelope keys, identity elements, and any other algebra a credential suite defines, is stored as suite-tagged bytes with a digest and interpreted only by the verifier the suite binds through the adapter registry; contract functions take that material as bytes with the suite identifier. Width-bearing deployment fields carry their length or are commitments. The deployment record carries the commitment-scheme identifier. The MVP suite's encodings are one realization of those records.

### EVM standards stated as protocol requirements

**Where it is fixed.** LC-13 states "The identity MUST be a contract account verified by ERC-1271", IW-07 states that registrations and bindings "MUST be EIP-712 typed data", and every identity-bound mutation takes an EIP-712 intent (`MVP Application Requirements.md`; `feature-spec.md`; `technical-requirements.md`, APIs). `signature/secp256k1` owns "EIP-712 typed data for registrations, bindings, and signed intents" (`dependency-map.md`), so a signature concrete owns a chain-layer message format.

**Position.** The requirements state an identity whose signer set is its device registry and a signed intent over the call's fields, chain, contract, nonce, and expiry. The EVM suite realizes them with ERC-1271 and EIP-712, and sponsorship with ERC-4337. The intent's typed form is a chain-family form held with the chain's forms, and the signature family signs the bytes it is handed. EIP-1193 and WalletConnect are wallet concretes and stay as they are.

## Order

The specifications precede the planning documents, and the planning documents precede the workplans, because each layer states what the layer below it cites. Within the specification layer and the planning layer, a document is corrected after every document it cites. Within the workplans, the pre-WBS sections precede the nodes, and nodes are corrected in Work Breakdown Structure order, so every corrected node's producers are corrected before it. Each document and each node is corrected once, for every coupling it carries.

A node marked complete whose content changes returns to unbuilt, and its files are rebuilt from the corrected node. A node the corrected dependency map adds inside the span the workplans already author is inserted at its dependency position. A node whose content no coupling touches is unchanged.
