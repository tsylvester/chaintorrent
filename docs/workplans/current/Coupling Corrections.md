# Coupling Corrections

## Purpose

This document holds the scope and order of the corrections that remove the couplings below from the specifications, the planning documents, and the workplan nodes. A coupling is a concrete form fixed at a point the architecture intends to be replaceable, with no adapter, declaration, or identifier between the concrete and the generic workflow that consumes it, or a seam whose owner the documents state inconsistently or not at all. The corrections change documents and workplan nodes. Implementation files follow from corrected nodes through the ordinary authoring path. The scope is complete when every proof in the completion check passes.

Each coupling below states where it is fixed and the position its correction establishes. The order section states how the corrections run, the layer sections state every document and node the corrections touch with their disposition, and the completion check states the proofs.

## Couplings and the positions their corrections establish

### Signature-scheme coupling

**Where it is fixed.** The generic signature interface carries no key recovery and no address derivation, and four planning documents place address derivation in `chain/evm_forms` (`system-architecture.md`, the adapter table's `chain` row; `technical-approach.md`, the family table's `chain` row; `technical-requirements.md`, the chain family's subsystem row and the file tree's `chain/` line). The `chain/evm_forms` row of `dependency-map.md` and the `chain/evm_forms` node of `ChainTorrent MVP 3.md` author no address derivation, and no other ticket or node authors it, so the operation that turns a public key into the identifier the EVM suite's identity account keys its signers by has no owner. The claim verifier's on-chain key is `VerifierKey`: `key bytes32`, `activeFrom uint64`, `revokedAt uint64` (`technical-requirements.md`, Database Schemas), with `rotateVerifierKey` and `revokeVerifierKey` in the contract API and vouchers "signed under the on-chain registered key" (`technical-requirements.md`, APIs). The stored key has a fixed width and no scheme identifier, and the contract verifies vouchers without the signature adapter the adapter registry binds per scheme, so moving the attestor to another signature scheme, or replacing it with a ZK-Email or DNSSEC verifier as R-16 anticipates, changes contract storage.

**Position.** Address derivation is an operation of the chain family's identity form. The chain family's form interface declares it beside the identity, entitlement, interval, chain-identifier, and signed-intent forms, and `chain/evm_forms` realizes it for the EVM suite over a public key's canonical bytes and its scheme identifier, so the forms concrete depends on no signature crate. Its output is the scheme-tagged key identifier the identity account keys its signer set by, one rule for every scheme, since the account verifies each signer through the signature adapter bound for that signer's scheme and no scheme needs a native address; the identity's own address is the account contract's, created at binding, and no form derives it. The claim verifier's on-chain key record carries a scheme identifier and a commitment to the attestation public key; the key itself travels in the calldata of `rotateVerifierKey`; the contract verifies each voucher through the signature adapter the adapter registry binds for the key's scheme. The claim verifier service signs under a custody-held key of a declared scheme, and the claim-verifier family's declaration names the scheme its vouchers carry. A further verifier form, a ZK-Email or DNSSEC verifier among them, is a further `claim-verifier` concrete and changes no contract storage. Ed25519 and secp256k1 remain the MVP's signature concretes.

### Solidity coupling

**Where it is fixed.** The R-14 row of `system-architecture.md`, Risk Mitigations, states "the on-chain registry binding the identity adapters, attestation verifiers, and token form" and names no delivery verifier, while every other statement of the adapter registry's bindings names it. Workplan nodes cite the generator's functions at `harness-crypto/generate/evm/...` while the nodes that author those functions, and every planning document, name them `harness-crypto/generate/solidity/...`: `pairing/bn254_arkworks` and `pairing/factory` in `ChainTorrent MVP.md`; `hash-to-scalar/keccak256`, `kem/bb1_depth_one`, and `kem/factory` in `ChainTorrent MVP 2.md`; `harness-crypto/vectors/cross_holder`, `harness-crypto/vectors/rerandomization`, `harness-crypto/vectors/non_convertibility`, `harness-crypto/vectors/malformed_capsules`, `harness-crypto/vectors/cross_set`, and `harness-crypto/vectors/statement_mutations` in `ChainTorrent MVP 5.md`. An implementer following those nodes looks for modules that do not exist.

**Position.** Every statement of the adapter registry's bindings names the complete set: the identity adapters, the signature adapter per scheme, the attestation verifier per ingest source, the entitlement token form, the delivery verifier per delivery-statement version and verifier form, and the payment-asset adapter per payment asset, each constructor-injected and immutable once bound. Every reference to the harness's generator names `harness-crypto/generate/solidity` and its functions by that path.

### Asset identity coupling

**Where it is fixed.** The specifications, the planning documents, and the workplans make a name the asset's identity. `cryptography.md` defines the identity hash as `BLAKE3(ecosystem ":" coordinates)`, a hash of a package registry's ecosystem token, package name, and version (The Hash-Card, the identity-hash row; Phase 1, the Canonical Identity Pre-Check and the identity-hash paragraph), and keys the Registry, entitlement binding, the asset-scope identity mapping, the publisher lineage's `asset_root`, and the delivery transcript on it. To compute it, the hashing family carries a digest operation and an identity-hash identifier beside its commitment operations (`dependency-map.md`, `hashing/blake3_bao`), and the Registry carries `Asset.ecosystem`, `Asset.nameHash`, `VersionIndex`, and `versionsByName` (`technical-requirements.md`, Database Schemas and APIs). `domain/asset_identity` fixes the package form, an ecosystem token, a name, and a version joined by `:` and `@` (`ChainTorrent MVP.md`); `domain/asset_identity_hash` restates the hash as a second domain type (`ChainTorrent MVP 2.md`); and the derivation context's canonical fields carry the ecosystem token, the name, and the version as text (`encoding/derivation_context`), so every wrapping key is derived over a package registry's naming convention. A git commit, a video, a song, or a container of files and folders has no ecosystem, name, and version, and identifying one under this design changes the Registry, the `domain` crate, and every suite's derivation context. The same specification already identifies content by its BLAKE3/Bao root (Distribution Invariants, Content Identity is Independent of Encryption Identity; What the Plaintext Fingerprint Buys; An Entitlement Binds to the Asset), so an asset carries two identities, one universal and one package-shaped, each restated in several places.

**Position.** The asset identity is the object's BLAKE3/Bao root: for a public asset the plaintext root, which the hash-card registers and every deployment of the asset carries, so anyone can prove a deployment decrypts to the asset it claims; for a private asset the ciphertext root, which the public record links to no other object, so no successor deployment and no plaintext is linkable to it. The hashing family owns the root type: `hashing/blake3_bao` produces it, the family's generic interface names it, and the family carries no digest operation and no identity-hash identifier. Every hashing operation is over bytes, so the hashing family depends on no encoding. The root type has one canonical field, its fixed 32 bytes. Every consumer of an asset's identity names the root type and takes that one field, and none declares an asset field of its own: the Registry's asset key, entitlement binding, the derivation context's asset component, the credential KEM's asset-scope identity bytes, the delivery transcript's asset field, and the harness's configured identities. The publisher lineage derives `asset_root` over the plaintext root, which a publisher always holds and which is the identity of every asset the MVP publishes; the private-asset case stays held where `cryptography.md`, Dependency Graph Privacy, holds private content. A name is a lookup, never an identity. An ingest or package-host adapter declares the namespace its names live in and maps a name to a root. The Registry holds alias records under a declared namespace and an opaque key, which no Registry field interprets; an alias key carries an append-only list of entries, each binding the key to one root and carrying the source's signed statement, for npm the string `name@version:integrity` with the registry signature over it, or that statement's recorded absence, and no entry is rebound or removed. An entry records nothing the asset's bytes contain: no digest apart from the one inside the signed statement, which the signature cannot be checked without, and no manifest. The asserting adapter writes an entry at registration, and further entries under one key are admitted under the abuse controls every registration carries. A client selects an entry only on evidence it holds independently of every registrant. An entry's signed statement authenticates itself however it travels, from the ledger, from the source, or relayed by any participant, and refutes an entry that recorded absence for bytes the source signs; its digest is checked against the client's lockfile `integrity`, or against the source when it is reachable, before anything is acquired. An entry with no signed statement is selected by decrypting its root and comparing the computed `integrity` with the client's lockfile or the source. Peer testimony is not evidence. The client verifies the decrypted bytes against the selected digest before committing them; an entry whose bytes fail is dead, an advisory records it, and resolution passes to the next entry the evidence selects. An alias with neither a signed statement nor a digest the client holds independently is ambiguous, and the client fails closed with an actionable result naming the competing roots. For npm the key is `name@version`, which the request carries, and npm's per-name version index is that adapter's own alias records. A name with no alias record is a First Finder event, which registers the root and the alias entry together. The registry serves every ingested version the client can decrypt with the source unavailable: the npm package host assembles a packument from the alias records, the version list, the decrypted tarballs' own `package.json`, each version's manifest, and the signed statements, each version's `integrity` and signature, and keeps no package metadata in a store of its own. Resolution selects each version from the alias list by npm's semver rules and reads its dependencies from its decrypted tarball, which the client acquires to install in any case. Dist-tags are the source's mutable state, carried in no bytes and signed by nothing, and are served best effort. The same bytes under two names are one asset, and a claim attaches to the asset. `DerivationContext` is housed in the sidecar layer, `workflows/sidecar/derivation_context`, which composes it for derivation, and its canonical description is beside it in the workflows crate, which depends on the encoding family; the `domain` crate holds no asset identity and no derivation context. The hashing family precedes every consumer of the root type. The root type has no node in the encoding family: the encoding family's first node is its first concrete, as every family's is, and a consumer that encodes the root takes its field in that consumer's own node.

### EVM-standards coupling

**Where it is fixed.** The chain-and-submission row of `dependency-map.md` has `chain/base`, the Base network concrete, author "the signed-intent form beside the identity, entitlement, interval, and chain-identifier forms". `system-architecture.md`, `technical-approach.md`, and `technical-requirements.md` place "the EIP-712 intent form" in `chain/evm_forms`. The `chain/evm_forms` row of `dependency-map.md` and the `chain/evm_forms` node of `ChainTorrent MVP 3.md` author no intent form. The documents therefore give the intent form two owners and the nodes give it none, and the owner the dependency map names is a network concrete, though EIP-712 belongs to the EVM suite that every EVM chain concrete shares.

**Position.** The chain family's form interface declares the signed-intent form as an associated type beside the identity, entitlement, interval, and chain-identifier forms. `chain/evm_forms` realizes it as EIP-712 typed data over the call's fields, chain, contract, nonce, and expiry, shared by every EVM chain concrete, and authors it together with address derivation. A consumer hands the form the call generically, an operation identifier and its named canonical field values, and the form interface names no EIP-712 type, selector, or ABI type; only the forms concrete maps a call to its typed-data struct. `chain/base` binds the forms `chain/create_chain_forms` resolves, the signed-intent form among them, and authors no form. The signature family signs the bytes the signed-intent form hands it and owns no message format, and the submission concretes submit what the form produces.

### Payment-asset coupling

**Where it is fixed.** `Lock` stores `entitlement uint256`, `buyer address`, `seller address`, `price uint256`, `expiry uint64` (`technical-requirements.md`, Database Schemas), and the contract API takes `lock(entitlement, seller, price, expiry)` (`technical-requirements.md`, APIs). No specification, planning document, family, declaration, or on-chain adapter names the asset a price is denominated in or paid with, so the chain's native asset is assumed wherever a price is set, locked, released, or refunded (`cryptography.md`, Economic Invariants and Phase 3, Payment Lock; `MVP Scope.md`, Paid Monetization and Transaction Flow Proof; `MVP Application Requirements.md`, LC-05, LC-10, RO-02, and AS-15). `MVP Scope.md`, Adapter Composition and Capability Declaration, names tokens in the class of components that are third-party now and first-party at maturity, and Paid Monetization states that moving a price from zero requires no client refactoring; a change of payment asset under the stated design changes the lock and settlement contracts and the client's acquisition path.

**Position.** A price is an amount of a named payment asset. A publisher's issuance policy names the payment asset of each price it sets, and a lock names the payment asset beside the price. On chain, `Lock` carries the payment-asset identifier, `lock` takes it, and the contracts move, release, and refund payment only through the payment-asset adapter the adapter registry binds for that identifier, constructor-injected and immutable once bound, behind the on-chain interface `IPaymentAsset`, whose MVP concrete settles in the chain's native asset. On the client, the `payment` family's factory owns `IPaymentAssetAdapter`, the payment-asset identifier, and the declaration of the assets a concrete settles, and `payment/native` is its MVP concrete. Entitlement acquisition reaches payment only through the payment factory, and the relayer's refusal to sponsor a paid acquisition is stated against the payment asset the lock names. The free path is a zero price, whatever the asset, and lock expiry and refund are unchanged. The priced dogfood transaction settles in Base's native asset as the MVP realization beneath this seam.

### Encoding type-name coupling

**Where it is fixed.** A canonical field kind, the vendor-free vocabulary the canonical-field contract `encoding/abi` authors (`FixedBytes32`, `FixedBytes20`, `Unsigned16`, `Unsigned32`, `Unsigned64`, `Unsigned256`, `Text`, `Bytes`), has a type name in each concrete encoding; under Ethereum ABI those names are `bytes32`, `bytes20`, `uint16`, `uint32`, `uint64`, `uint256`, `string`, and `bytes`. The mapping is a fact of the ABI encoding, and the `encoding/abi` row of `dependency-map.md` already states part of it ("each named as a width, mapped to its ABI type by this concrete"). Yet the complete table is owned by a harness module: `harness-crypto/generate/solidity/render` "owns ... the table from canonical field kinds to ABI type names" (`dependency-map.md`, the `render` row, the `constants` row, and the Conflict Flags entry "The generate concrete is an adapter over functions it owns"; `system-architecture.md`, Conflict Flags, "The Solidity generate concrete is an adapter over functions it owns"; `milestones.md`, Delivery proof and on-chain verifier, the `render` and `constants` scope lines; `technical-requirements.md`, the file tree's `Constants.sol` and `VectorRecords.sol` lines; the `render` and `constants` nodes of `ChainTorrent MVP 3.md`, through the type `SolidityAbiType`).
`chain/evm_forms` needs the same table to name the members of its EIP-712 typed-data structs, so the corrected node would hold a second copy. One fact with two owners is a seam whose owner the documents state inconsistently, which this document defines as a coupling.

**Position.** The encoding family owns the type name an encoding gives each canonical field kind, because the type name is a property of the encoding, as every serialization framework places it: a type describes itself in an abstract vocabulary and the format's encoder maps that vocabulary to the format's types (`serde`'s data model; `alloy`'s sol types carrying their Solidity names for EIP-712 `encodeType`).
- The encoding factory's interface declares, on `IEncoderAdapter`, an operation that takes a canonical field kind and returns the encoding's type name for it, a validated text type the factory owns, `EncodingTypeName`. The signature names no ABI, Solidity, or EIP-712 term. Every kind has exactly one name, so the operation is total and returns no error.
- `encoding/abi` realizes it with the table above, a fixed twenty-byte kind always `bytes20` and never `address`. It is the only place the table exists. The family's mock returns a declared mock name per kind.
- A consumer that needs type names reads them from the encoder it is handed, never from a table of its own. A consumer that requires a particular encoding's names declares the encoding identifier it requires, and the factory or family-owned function that constructs that consumer admits the handed encoder only when the encoder's declaration carries that identifier, refusing it otherwise with no side effect.
- `chain/evm_forms` is constructed over a borrowed encoder, as the proof and generate concretes are; it reads each EIP-712 struct member's type name from that encoder, and its declaration names the encoding identifier it requires, ABI. `chain/create_chain_forms` takes the borrowed encoder in its deps and admits it against that declaration.
- `harness-crypto/generate/solidity/render` stays pure, reading no adapter: it owns no table and takes each record member's type name, already resolved, as data. It keeps only Solidity-language facts, such as which kinds a decoded local variable holds in `memory`, for which each member also carries its canonical field kind.
- `harness-crypto/generate/solidity/constants` reads each transcript field's type name from the borrowed encoder its deps carry. `harness-crypto/generate/solidity` resolves every record member's type name from its borrowed encoder before calling `render`.

Every document and node this coupling touches is listed under the layer sections below. A document or node already marked `[✅]` whose content this coupling changes is marked `[ ]` again and corrected for this coupling only; its earlier corrections stand.

## Order

The specifications precede the planning documents, and the planning documents precede the workplans, because each layer states what the layer below it cites. Within the specification layer and the planning layer, a document is corrected after every document it cites. Within the workplans, the pre-WBS sections precede the nodes, and nodes are corrected in Work Breakdown Structure order, so every corrected node's producers are corrected before it. Each document and each node is corrected once, for every coupling it carries.

A node marked complete whose content changes returns to unbuilt, and its files are rebuilt from the corrected node. A node the corrected dependency map adds inside the span the workplans already author is inserted at its dependency position. A node whose content no coupling touches is unchanged.
