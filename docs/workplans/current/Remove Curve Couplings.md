# Remove Curve Couplings

## Purpose

Adding a pairing concrete is one change inside the pairing family: its module, its variant in the selection enum and the error enum, its entry in `PAIRING_CONCRETES`, its arm in the factory, and the variants of the family's own declaration enums a new curve brings. Every consumer reaches the new concrete through the factory and reads what it needs from the concrete's declaration, so no consumer, configuration file, generated-file consumer, or deployment script changes.

The harness runs a matrix of the adapters its configuration selects. With no configuration file and no override it runs the pairing family's and the encoding family's entire declared sets, so its outcome shows every combination of the available adapters; a configuration file or an override narrows the sets. Every cell of the matrix runs as far as it can, and the run reports every cell's outcome, a refusal included.

The specifications, the planning documents, and the workplans currently enumerate curves outside the pairing family, key configuration and generated files by curve, and state the run per declared curve. This scope replaces every such statement with the form the next section states.

## The Agnostic Form

Every entry in the layers below applies these statements. An entry names where a document departs from them, and the corrected text states them in that document's own terms and at that document's own resolution. Each statement ends with the coupled forms it replaces, which are the phrases to search a document for.

- **The matrix.** The harness configuration holds a list of pairing concretes, a list of target-group encoding identifiers, and a list of encodings. A list the configuration does not carry is the owning family's declared set: `PAIRING_CONCRETES`, the pairing family's `TARGET_GROUP_ENCODING_IDENTIFIERS`, and the encoding family's declared selections. A list the configuration carries narrows the set to the members it names: each text value names a member of the family's declared set by the rule `harness-crypto/config/admit_selections` already applies to every selection, equality with the member's `Debug` text through `member_named`, a value naming none is refused with its document path, and the harness holds no arm per concrete. The shipped defaults carry none of the lists. A cell is one member of each list. Every other family keeps its one configured selection.
  - Replaces: the `curves` entries naming one pairing concrete per curve; the refusals of a curve served twice and of "a declared curve no entry serves"; the separate list of pairing concretes the benchmark measures; `DECLARED_PAIRING_CURVES`, `DeclaredPairingCurve`, `pairing_curves`, and "each curve the pairing family declares"; "the concrete named for each declared curve".
  - A statement that the benchmark's measurements set "the configuration's shipped concrete per curve" becomes: the benchmark records each selected concrete's measurements, and the harness ships no pairing default for them to set.
- **The target-group encoding identifier is an axis.** For a cell the run hands `create_pairing` the cell's pairing concrete and the cell's identifier. The factory admits a concrete that declares the identifier and refuses one that does not, and the refusal is that cell's outcome. No value pairs an identifier with a concrete or with a curve, in configuration or in code.
  - Replaces: "the target-group encoding identifier per curve"; an identifier carried beside a concrete in one configuration entry; an identifier chosen for a concrete by a table or a `match`.
- **The run.** `harness-crypto/run` iterates the selected pairing concretes in list order and, within each, the selected identifiers in list order. For each such pair it calls `create_pairing` with the benchmark as the consumer. Then, for each selected encoding in list order, it calls `create_pairing` with `harness-crypto/run/pairing_consumer` as the consumer, the cell's encoding carried to that consumer as its encoding selection. No refusal ends the run: a refusal from any call is the outcome of that pair or that cell, and the next call is made, so the run reaches every compatible combination however many incompatible ones precede it. The run's outcome holds every pair's benchmark outcome and every cell's outcome once, in iteration order, each naming its members.
  - A pair or cell has one of three outcomes. Completed: it ran to its end. Incompatible: a family's factory refused the combination at its admission, before constructing anything. Refused: any other refusal, a cell with no deployment record among them.
  - An incompatible pair or cell is a reported outcome and not a failed run. The run succeeds when every pair and cell is completed or incompatible. Where any is refused, the error arm carries every pair's and every cell's outcome, as the documents now state per declared curve.
  - Replaces: "for each curve the pairing family declares", "runs each curve the pairing family declares", "per declared curve", "in declared order", "the next declared curve", and an outcome, a report, or a measurement stated "per curve".
- **No positional matching.** No value is matched to a concrete, a curve, or a cell by its position in a list.
  - Replaces: `config.verifiers[i]`, "at index `i`", "one verifier concrete per declared curve".
- **Names come from declarations.** Each pairing concrete's declaration supplies the concrete's name and its curve's name. The encoding family's declaration supplies the encoding's name. Each family's mock concrete supplies its own. A name is read from the received type's declaration at the level that receives the adapter and is handed inward. No configuration value, literal, or table supplies a directory name or a deployment-record key.
  - Replaces: curve directories and curve labels configured or keyed by curve; a directory or key taken from the `Debug` text of `PairingCurve`; the keys `bn254` and `bls12_381` written in a configuration file or a script.
- **The cell directory.** The generate concrete writes a cell's files in the generated directory joined with the pairing concrete's name and then the encoding's name, each name admitted through `GeneratedFileName` and a refusal returned as the generate concrete's own error. Both libraries of one curve therefore write separate directories, and no cell rewrites another cell's files.
  - Replaces: `<curve>/`, "one directory per curve", "the curve directory", `SolidityCurveDirectories`, `curve_directories`, `by_curve`.
- **What a cell directory holds, and what sits outside it.**
  - A cell directory holds the cell's vector files and the cell's values: the curve's name, the precompile encoding the pairing declares, as the text that names it, the scalar field's order, the two generators' precompile encodings, and whether the verifier has second-group arithmetic.
  - The cell's values are the one record of an enumerated vector kind the generate concrete declares, written and read as every vector file is, its file, struct, decode function, and path constant names configured as every kind's are. `harness-crypto/generate/solidity/constants` returns that record, with its canonical description and member names, beside the library entries.
  - The constants library holds only the values that are the same for every cell: the domain tags, the delivery-statement version, the purpose codes, and the transcripts' field sequences.
  - The constants library and the vector-record library are written in the generated directory outside every cell directory, each under its one configured file name and library name.
  - The vector-record library's path constant for a kind holds the kind's configured file name alone, and a reader joins it to the cell directory it is reading.
  - Replaces: per-curve library names and identifiers, `SolidityCurveLibraryNames`, `SolidityCurveLibraries`, a constants library "per curve", the scalar field's order, the generators' encodings, and the verifier form as constants-library entries, and a path constant holding a path through a curve directory.

- **Tests and deployment read the generated directory at runtime.** The suite's Foundry tests enumerate the cell directories under the generated directory and run once per cell directory, reading that directory's values and its vector files. `contracts/evm/deploy` enumerates the same directories, reads each one's values, and deploys the delivery verifier once per distinct curve name, in the verifier form that curve's values state and constructed with that curve's values. It emits each address as the deployment record keyed by that curve name. Neither the tests nor the script names a curve, a concrete, or a count of either.
  - Replaces: "one key per configured curve label, `bn254` and `bls12_381`", "the verifier on each curve form" stated over a fixed pair of forms, and a test that names the curve whose files it reads.
- **Deployment records are looked up by curve name.** The configuration holds the deployment records as a map from curve name to address, admitted value by value, a malformed address refused with its key. No key is checked against a set of curves. The shipped defaults hold no record, and the layer `contracts/evm/deploy` emits supplies them. `harness-crypto/run/pairing_consumer`, which receives the pairing, reads the curve's name from its declaration, looks the record up, and hands the result inward.   - Replaces: deployment records "keyed by each admitted curve's name" with the admission refusals of "a curve with no record" and "a key naming no admitted curve"; "the configured verifier concrete of the curve it composes, which carries that curve's deployment record"; a first run's refusal stated as "nothing being deployed at the configured address".
- **Tests carry no table of curve facts.** No expectation is keyed on which curve has second-group arithmetic or which directory belongs to which concrete, so a further concrete needs no test edit. - **The generate family owns its sizing types.** `VectorCount` and `MsmTermCount` are owned by the generate family's factory interface. `harness-crypto/generate/solidity/group_vectors`, the first source file that requires them, declares them there, and `harness-crypto/generate/solidity`, the family's first concrete, adds the rest of that interface.
  - Replaces: ownership of the two types by `group_vectors` itself, and the factory interface naming them through the Solidity concrete's surface.

## The `harness-crypto/generate/solidity` Node

The node carries more of the couplings than any other, so its corrections are stated here in full. Each item names the node's own elements and identifiers; none is located by line.

**The directory is configured instead of read**
- `SolidityCurveDirectories … by_curve: BTreeMap<PairingCurve, GeneratedFileName>, the configured directory of each curve`; "the curve directory the entry `curve_directories.by_curve` holds for `P::DECLARATION.curve`".
- Delete `SolidityCurveDirectories`, its constructor params, builders, and invalidators, and the `curve_directories` settings field. The directory is the cell directory: the generated directory joined with the name the received pairing's declaration supplies for its concrete and the name the borrowed encoder's declaration supplies, each admitted through `GeneratedFileName`.
- The node's title sentence and its objective state the cell directory in place of "the directory configured for the declared curve" and "the curve directory". 

**Library names are keyed per curve**
- Each library has one configured file name and one configured library name, used unchanged for every cell, as the technical requirements' generated-directory entries state: "its file and library names the configuration's".
- The libraries hold only what is the same for every cell and are written in the generated directory outside every cell directory. The cell's values are the record of the declared enumerated kind, written in the cell directory beside that cell's vector files.
- Delete the objective's requirement that each curve's constants library and records library carry that curve's own configured names so that one Solidity file imports them together as distinct identifiers. Nothing consumes it but a source that lists every curve.
- Delete per-curve library naming entirely: `SolidityCurveLibraryNames`, `SolidityCurveLibraries`, every `by_curve` map, and their constructor params, builders, and invalidators.
- The path constant the node hands `render` for a kind is the kind's configured file name alone.

**The cell's values are a declared kind**
- The concrete's declaration names one further kind, enumerated and not gated on second-group arithmetic, holding the cell's values record `constants` returns. The concrete encodes and writes it as it writes every kind, under the names its per-kind settings carry.
- The curve's name in that record is the name the received pairing's declaration supplies.

**The `MissingCurveSettings` refusal**
- It comprises the `MissingCurveSettings { curve }` variant of the concrete's error; the `Curve settings` branch of the interaction spec; the unit blocks `emit_selects_the_mock_curves_directory_and_library_names` and `emit_refuses_a_curve_with_no_settings_entry`; and the own entry and private integration block `a_curve_with_no_settings_entry_is_refused_with_its_curve`.
- Delete the variant, the branch, both unit blocks, the own entry, and the private block. Replace the mock-curve unit block with a derivation block: over the pairing family's and the encoding family's mock concretes, the cell directory equals a literal written in the test, and the libraries are written outside it under their configured names.

**`DECLARED_PAIRING_CURVES` names concretes inside the pairing factory interface**
- Delete the node's whole `adapters/pairing/src/factory/interface.rs` element; the `role` line that declares `PairingCurve`'s derives, `DeclaredPairingCurve`, `DECLARED_PAIRING_CURVES`, and `pairing_curves`; that file in the `module` element's file list; and every mention of those items and of `by_curve` in `deps` and `context_slice`. The `Ord` derive goes with them.
- A derive on `PairingCurve` that another node still requires is declared by that node, as the first file that requires it.

**Test expectations hard-code which curve is which**
- The second-group gate and the names are read from the received pairing's declaration inside the case consumer, which is the level that receives it. The derivation itself is proven once in the unit test, over the mock pairing, against literals written in the test, so no integration block asserts a value against itself.

**The family's sizing types come from inside the Solidity concrete**
- `VectorCount` and `MsmTermCount` are declared in the generate family's factory interface by `group_vectors`, the first source file that requires them. This node and `group_vectors`' sibling functions name them from there, and the factory interface's import of them from the Solidity concrete's surface is deleted.

**A missing size is reported as the concrete's own error**
- A missing size becomes a family flavor of `EmitErrorReturn`; a missing name stays the concrete's own error.

## Producers

Each producer below is corrected before any node that consumes it.

- **The pairing declaration's names.** `pairing/bn254_arkworks` authors `PairingDeclaration`; it gains the concrete's name and the curve's name. Each pairing concrete's `DECLARATION` sets both, and the family's mock concrete sets its own.
- **The encoding declaration's name.** `encoding/abi` authors the encoding family's capability declaration; it gains the encoding's name. The concrete's declaration sets it, and the family's mock concrete sets its own.
- **The cell's values record.** `harness-crypto/generate/solidity/constants` returns it beside the library entries and owns its record type, canonical description, and member names. The scalar field's order, the generators' encodings, and the verifier form leave the library entries it returns.
- **The sizing types.** `harness-crypto/generate/solidity/group_vectors` declares `VectorCount` and `MsmTermCount` in the generate family's factory interface. 

## Order

The specifications precede the planning documents, and the planning documents precede the workplans, because each layer states what the layer below it cites. Within the specification layer and the planning layer, a document is corrected after every document it cites. Within the workplans, the pre-WBS sections precede the nodes, and nodes are corrected in Work Breakdown Structure order, so every corrected node's producers are corrected before it. Each document and each node is corrected once, for every coupling it carries.

A node marked complete whose content changes returns to unbuilt, and its files are rebuilt from the corrected node. A node the corrected dependency map adds inside the span the workplans already author is inserted at its dependency position. A node whose content no coupling touches is unchanged.
