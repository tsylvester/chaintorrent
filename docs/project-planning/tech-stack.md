# Tech Stack Recommendations

The technologies the ChainTorrent MVP is built with. The marked kinds are members of a statement-class identifier with one canonical spelling per member — **fixed**, **recommended**, **external-context** — used as record keys and comparisons rather than text. **Fixed** means a source document decides it: the [MVP Application Requirements](../research/MVP%20Application%20Requirements.md) fix the languages and runtimes, [cryptography.md](../research/cryptography.md) and [MVP Scope](../research/MVP%20Scope.md) fix the primitives and standards, and the [product requirements](product-requirements.md) record the launch network and platform matrix. **Recommended** means this document proposes it and nothing in the sources decides it; each such choice is a candidate the first node to consume it may confirm or replace, and none becomes a requirement by appearing here. Crate versions are external context, not repository facts, and the node that pins a crate confirms its version.

## Frontend Stack

**Fixed.** Deployable applications with a graphical interface use Tauri; headless services and the CLI are Rust without Tauri. The Visual Studio Code extension is TypeScript because the extension host requires it. The npm bootstrap package contains the minimum JavaScript or TypeScript that npm lifecycle conventions require. TypeScript surfaces are thin shells that own no protocol rule, cryptographic decision, entitlement logic, package resolution, or workflow state, and any additional TypeScript module must name the host constraint that prevents Rust. Supported platforms are the platform identifier's declared members: Windows, macOS, and Linux.

**Recommended.**

| Surface | Choice | Note |
| --- | --- | --- |
| Desktop application | Tauri 2 stable | The MVP targets the stable line. Tauri's Rust core hosts the same workflow crates the daemon uses; the webview shows state, it does not compute it |
| Desktop webview UI | Plain TypeScript with a small component library, no framework mandated | The desktop surface is configuration, status, diagnostics, and consent; it does not need a large framework. Whichever is chosen, the UI calls Tauri commands that call shared Rust, and its status, diagnostics, and consent states are typed identifiers, never label text |
| Visual Studio Code extension | TypeScript against the VS Code extension API, spawning or connecting to the daemon over the authenticated local IPC | The extension bundles or downloads the signed Rust installer and never reimplements it |
| npm bootstrap package | A minimal `postinstall`-free package exposing a `bin` that invokes the signed Rust installer | Avoiding `postinstall` keeps the package from executing on transitive install; the developer runs the binary deliberately through `npx chaintorrent`, one command with no install-time script, which is the consent posture MVP Scope requires and the command SI-02 names |
| CLI | Rust, `clap` for argument parsing | Scriptable consent, configuration, diagnostics, jobs, and the recovery actions repair and uninstall, each carried as a typed action identifier; not a resolver |
| Project site, education tier | A static site plus a WebAssembly build of the domain, pairing, hashing, KEM, and payload-cipher crates through `wasm-bindgen`, run against a bundled sample deployment | Fixed in scope by MVP Scope's Project Seed Host and Site: real resolution, Bao verification, and decapsulation in the browser with no service on the read path; no account; the demonstration states that seeding and the CAS do not run in a browser. the pairing concretes and `blake3` compile to WebAssembly; the sample deployment is generated by the `sample_deployment` node of the payload cipher milestone, since it needs the cipher |
| Website account, rendezvous, remote head, hosted instance | Deferred to V2 | MVP Scope, Website, Account, and Remote Head. When scoped: OpenID Connect for provider sign-in, Sign-In with Ethereum style signed challenges for identity linking, an outbound-only rendezvous relaying end-to-end encrypted sessions, and a browser UI over the daemon's authenticated IPC. These members and their sign-in-provider variants stay outside every current declared set and identifier variant until real implementations exist |

## Backend Stack

**Fixed.** All deployable applications are Rust. Shared protocol rules, application workflows, cryptography, storage, networking, credential delivery, and adapter contracts are Rust libraries so that CLI, desktop, daemon, and harness execute one behavior. Three dependency rings, protocol and domain, application workflows, adapters and host shells, with dependencies pointing inward. Every family has declaration lookup, selection admission, and composition admission ahead of its factory, plus concrete settings-document guards and settings admission only where the concrete has settable values; every adapter declares capabilities, version, and compatibility through its declaration, and composition fails closed before construction or any operation, not merely at resolution after construction. EVM contracts compile to EVM bytecode from the source language the contract suite declares, Solidity in the MVP. The launch network is the chain-network identifier's declared member Base, an OP Stack L2, with Base Sepolia for testing.

## Data Platform

**Fixed.** Two content-addressed stores with separate owners and lifecycles: the plaintext CAS, owned by the client and keyed by content hash, and the ciphertext store, owned by the seed-host member and keyed by ciphertext root. A custody store that holds identity, envelope, issuance, and seed material and per-entitlement envelopes, and never the decrypted credential or piece-group keys. A durable, checkpointed, idempotent job store. A versioned configuration registry. On-chain state as the technical approach's Data section describes. Envelopes and proofs in calldata and events, recoverable from any honest full-history node.

**Recommended.**

| Store | Choice | Basis | Note |
| --- | --- | --- | --- |
| Durable job store and local indexes | The `storage` family, its factory owning the key-value store interface with tables, transactions, and checkpoints and the storage-engine member identifier; `storage/redb` over `redb` 4.3.0 | Recommended | An embedded, transactional, pure-Rust key-value store; ACID transactions give the checkpointing that XA-03 and FF-03 require without an external database process; the job engine, configuration registry, and every index consume the family's settings-carrying admitted selection and name no store library, with storage composition admission completed before any store effect |
| Plaintext CAS | The `cas` family, its factory owning commit, serve, pin, and reuse metrics with quota and eviction decisions carried as typed outcome identifiers; `cas/filesystem` with a content-hash directory layout of verified tarballs, atomic rename on commit, and its index through the storage family; package managers extract per project and nothing links into the store | Recommended | PR-04's atomic commit is a temp-file-then-rename discipline; reuse is at the tarball, so no linker and no shared installed tree, which a pnpm-style store would need and the MVP does not promise; the member is selected through settings-carrying admission and its composition admitted before any store effect |
| Ciphertext store | Inside `seed-host/owned`, the filesystem keyed by ciphertext root with an index through the storage family recording the holding-kind identifier | Recommended | SW-05 requires obligated versus voluntary holdings recorded as holding-kind members; under `seed-host/rqbit` the store is whatever the rqbit application uses and the concrete translates; the seed-host member is selected through settings-carrying admission with composition admitted before any store effect |
| Custody store | `custody/local_keystore` over the OS credential store through `keyring` 4.2.0, holding a wrapping key; envelope keys, identity keys, and per-entitlement envelopes encrypted under it on disk | Recommended | The accepted default and the custody family's first member: a local keystore under Windows Credential Manager, macOS Keychain, or Linux Secret Service. Credential stores hold small secrets, so the pattern is a wrapping key in the store and an encrypted blob on disk; no other module touches the credential store |
| Chain state reads | The chain family's quorum view over `chain/base`, `alloy` view calls against more than one configured endpoint of the chain-network member Base, aggregated and failing closed on disagreement with each view outcome a typed value | Recommended | XA-06; the endpoint selections are admitted through the chain family's settings-carrying selection and its composition is completed before any read |
| Envelope recovery | Event and calldata reads from a full-history endpoint of the chain-network member Base through `chain/base`, the selection admitted and composition completed before any read | Recommended | CD-04; a configured archive endpoint is an operating dependency to state |
| Metrics store | `telemetry/local_metrics`, local append-only metrics under the daemon with the RO-03 schema — its categories typed identifiers — over the storage family, exported through the diagnostics API after telemetry and storage composition admission | Recommended | No external metrics service is required by the sources |

## DevOps Tooling

**Fixed.** Signed, atomic, schema-aware, reversible updates. Installation through one Rust coordinator on the platform identifier's declared members Windows, macOS, and Linux, with service lifecycle under each platform's service manager or an equivalent persistent user service, every platform's lifecycle and artifact-scheme members and their settings admitted ahead of each factory and lifecycle, artifact-verifier, IPC, and chain composition admission completed before installation, update, deployment, or service effects; chain forms selection and composition admission completes separately before deployment or signed-intent effects, the chain declaration's forms requirement compared against the resolved forms declaration. The packaged MVP runs without a developer toolchain. The repository ships unit, integration, and end-to-end facilities and every requirement's proof class maps to one. The verifier is deployed to the chain-network member Base Sepolia by `contracts/evm/deploy` in the harness grouping, and the harness's verifier family reaches it without deploying it.

## Security Tooling

**Fixed.** Every input untrusted until narrowed by its owning family at its boundary — every descriptor, adapter response, IPC request, and proof input — each validation refusal a typed outcome; fuzzing at every adapter contract; decrypt-capable material memory-only and zeroized at every transition, each lifecycle transition outcome a typed value; telemetry scanned for sensitive fields, the scan outcome a typed value; the Rust verifier and the deployed contract cross-verified bit for bit; external cryptographic review before any priced deployment.

**Recommended.**

| Concern | Choice | Note |
| --- | --- | --- |
| Zeroization | `zeroize` on every type holding a credential, piece-group key, cipher state, or scalar, with `Drop` implementations | CR-07 |
| Constant-time operations | `subtle` for comparisons over secret material; curve arithmetic from libraries that document constant-time scalar multiplication | The pairing libraries below document their timing posture per operation |
| Dependency auditing | `cargo-audit` and `cargo-deny` in CI, with a license allowlist for the source-available posture | Also enforces the licensing decision on the dependency tree |
| Fuzzing | `cargo-fuzz` targets for every adapter boundary, descriptor parser, IPC request, and proof verifier input, each input class narrowed by its owning family's admission before use | XA-01, CR-06 |
| Contract analysis | Foundry's fuzz and invariant testing plus a static analyzer such as Slither in CI | External context for Slither; the mutation and replay vectors are Foundry tests |
| Telemetry scanning | A test that greps every log, trace, metric, and crash artifact produced by the acceptance run for known secret encodings and fails on any hit, the scan outcome a typed value and no `Debug` or `Display` rendering ever a document key | RO-03, AS-20 |
| Secret-free diagnostics | A `domain` secret type that implements no formatting or serialization trait, exposes the wrapped value only through an explicit accessor, and zeroizes on drop, proven at compile time | Type-level enforcement rather than review; the tracing layer carries correlation and does no redaction, and no `Debug` or `Display` output becomes a record key or document value |
| Workspace lints | The manifest's lint table forbids `unsafe_code` and denies clippy's `unwrap_used`, `expect_used`, `panic`, and `as_conversions` in production code, exempting test modules and the `mocks` feature | The typing rules checked by `cargo clippy` on every edit |
| Signing-key custody | Release signing keys under the same custody discipline as issuance material, the signing scheme and artifact identity carried as owning identifiers, held off the CI runner with a rotation path | NF-S11, XA-08 |

## Shared Libraries

**Fixed primitives.** BLAKE3 with Bao verified streaming for integrity; AES-256-CTR with a 64-bit IV and 64-bit block counter for the payload; the signature-scheme identifier's members Ed25519 and ML-DSA-65 at the handshake and content-signing layers, the scheme a layer signs under admitted from configuration by the signature family and resolved through declarations rather than algorithm-name text; secp256k1 at the EVM chain layer; Type-3 pairing groups on the curve identifier's members BN254 and BLS12-381 for the credential KEM, envelope, and delivery proof; a domain-separated KDF and hash-to-scalar, each a provider-owned identifier with total spellings and applicable wire codes; W3C DID Documents as the identity family's DID binding-form identifier.

## Additional Content

**Why nothing here is a requirement.** The Application Requirements fix languages, runtimes, primitives, standards, and structure, and they say that a later workplan may split or combine implementation units without changing a requirement. A library is an implementation unit. Naming one here records a recommendation; no recommended library or external-context entry becomes a production variant or a requirement by appearing here — a variant exists only when a real member is chosen and exists. The node that first consumes it makes the choice and admits the real implementation, its settings, and its provider-owned identifiers through the owning family's surfaces before use, and the standards that govern that node, not this document, decide whether it conforms.

**External context.** Crate versions, Foundry, Slither, Sigstore, OpenZeppelin, the bundler providers, and the wallet providers are external context, not repository facts, and no entry is a production identifier variant until a consuming node admits a real implementation.

**Relationship to the other documents.** The technical approach's family table names the MVP member beneath each family's factory surface; this document names the libraries those members are built from, and each library appears only inside the member that wraps it. The dependency map's harness tickets consume the pairing, KDF, and EVM choices here first, through the families' declaration, selection, and composition surfaces, and the technical approach, dependency map, and workplan place every producer, provider-owned identifier, and admission function before its consumers. The product requirements' Resolved Positions hold the decisions this document treats as fixed: the chain-network member Base, the curve members BLS12-381 primary with BN254 retained, the platform members Windows, macOS, and Linux, and the crate-per-family workspace in which each crate is its family's factory surface.
