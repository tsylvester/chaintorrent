# Tech Stack Recommendations

Draft, 2026-09-23. The technologies the ChainTorrent MVP is built with. Two kinds of statement appear and are marked throughout. **Fixed** means a source document decides it: the [MVP Application Requirements](../research/MVP%20Application%20Requirements.md) fix the languages and runtimes, [cryptography.md](../research/cryptography.md) and [MVP Scope](../research/MVP%20Scope.md) fix the primitives and standards, and the [product requirements](product-requirements.md) record the launch network and platform matrix. **Recommended** means this document proposes it and nothing in the sources decides it; each such choice is a candidate the first node to consume it may confirm or replace, and none becomes a requirement by appearing here. Crate names were checked against crates.io on 2026-09-23 with the latest version and last-update date noted, so that nothing is recommended from memory; those checks are external context, not repository facts.

## Frontend Stack

**Fixed.** Deployable applications with a graphical interface use Tauri; headless services and the CLI are Rust without Tauri. The Visual Studio Code extension is TypeScript because the extension host requires it. The npm bootstrap package contains the minimum JavaScript or TypeScript that npm lifecycle conventions require. TypeScript surfaces are thin shells that own no protocol rule, cryptographic decision, entitlement logic, package resolution, or workflow state, and any additional TypeScript module must name the host constraint that prevents Rust. Supported platforms are Windows, macOS, and Linux.

**Recommended.**

| Surface | Choice | Note |
| --- | --- | --- |
| Desktop application | Tauri 2 stable | Tauri 3 is in alpha as of 2026-09; the MVP targets the stable line and migrates when 3 is stable. Tauri's Rust core hosts the same workflow crates the daemon uses; the webview shows state, it does not compute it |
| Desktop webview UI | Plain TypeScript with a small component library, no framework mandated | The desktop surface is configuration, status, diagnostics, and consent; it does not need a large framework. Whichever is chosen, the UI calls Tauri commands that call shared Rust |
| Visual Studio Code extension | TypeScript against the VS Code extension API, spawning or connecting to the daemon over the authenticated local IPC | The extension bundles or downloads the signed Rust installer and never reimplements it |
| npm bootstrap package | A minimal `postinstall`-free package exposing a `bin` that invokes the signed Rust installer | Avoiding `postinstall` keeps the package from executing on transitive install; the developer runs the binary deliberately, which is the consent posture MVP Scope requires |
| CLI | Rust, `clap` for argument parsing | Scriptable consent, configuration, diagnostics, jobs, repair, uninstall; not a resolver |
| Project site, education tier | A static site plus a WebAssembly build of the domain, pairing, hashing, KEM, and payload-cipher crates through `wasm-bindgen`, run against a bundled sample deployment | Fixed in scope by MVP Scope's Project Seed Host and Site: real resolution, Bao verification, and decapsulation in the browser with no service on the read path; no account; the demonstration states that seeding and the CAS do not run in a browser. arkworks and `blake3` compile to WebAssembly; the sample deployment is generated by the harness |
| Website account, rendezvous, remote head, hosted instance | Deferred to V2 | MVP Scope, Website, Account, and Remote Head. When scoped: OpenID Connect for provider sign-in, Sign-In with Ethereum style signed challenges for identity linking, an outbound-only rendezvous relaying end-to-end encrypted sessions, and a browser UI over the daemon's authenticated IPC |

## Backend Stack

**Fixed.** All deployable applications are Rust. Shared protocol rules, application workflows, cryptography, storage, networking, credential delivery, and adapter contracts are Rust libraries so that CLI, desktop, daemon, and harness execute one behavior. Three dependency rings, protocol and domain, application workflows, adapters and host shells, with dependencies pointing inward. Every adapter declares capabilities, version, and compatibility, and composition fails closed at resolution. EVM contracts are Solidity. The launch network is Base, an OP Stack L2, with Base Sepolia for testing.

**Recommended.**

| Concern | Choice | Verified | Note |
| --- | --- | --- | --- |
| Async runtime | `tokio` | Widely used; not re-verified | The daemon, seed host, relayer, verifier, and harness are all long-running async services |
| Workspace layout | One Cargo workspace; a domain crate; one crate per adapter family; one crate per deployable | Per the accepted default in the product requirements | Crate boundaries are the ring boundaries, so a domain crate that depends on Tauri or a chain SDK fails to compile rather than to review |
| Local IPC | Unix domain sockets on macOS and Linux, named pipes on Windows, with a request-authenticated framing layer | Recommended | XA-02 requires authenticated least-privilege local APIs; the transport is per platform, the authentication is shared Rust |
| EVM client | `alloy` 2.5.0, updated 2026-09-23 | Yes | Contract bindings, transaction submission, EIP-712 typed data, view calls, and event reads; the successor to ethers-rs and the maintained choice |
| Solidity toolchain | Foundry: `forge` for build and test, `anvil` for a local chain, `cast` for scripting | External context | Foundry's test harness is the natural place for the mutation and replay vectors the verifier must reject; Anvil provides the local chain before Base Sepolia |
| Contract language | Solidity, with the pairing library over the EIP-196, EIP-197, and EIP-2537 precompile addresses | Fixed language; library recommended | Constants and test vectors generated from the Rust reference per the accepted default |
| Serialization | `serde` with a canonical binary encoding for anything hashed or signed | Recommended | Canonical encoding is load-bearing for the delivery statement and the hash-card; a non-canonical encoder is a correctness bug |
| Structured logging and tracing | `tracing` with an OpenTelemetry exporter | Recommended | RO-04 requires one request correlated across package host, CAS, swarm, chain, custody, decryption, and background work |
| Configuration | Versioned TOML in the configuration registry with schema migrations | Recommended | IC-04 requires a versioned registry with no raw secrets; secret references point into custody |

## Data Platform

**Fixed.** Two content-addressed stores with separate owners and lifecycles: the plaintext CAS, owned by the client and keyed by content hash, and the ciphertext store, owned by the seed host adapter and keyed by ciphertext root. A custody store that holds identity, envelope, issuance, and seed material and per-entitlement envelopes, and never the decrypted credential or piece-group keys. A durable, checkpointed, idempotent job store. A versioned configuration registry. On-chain state as the technical approach's Data section describes. Envelopes and proofs in calldata and events, recoverable from any honest full-history node.

**Recommended.**

| Store | Choice | Verified | Note |
| --- | --- | --- | --- |
| Durable job store and local indexes | `redb` 4.3.0, updated 2026-09-15 | Yes | An embedded, transactional, pure-Rust key-value store; ACID transactions give the checkpointing that XA-03 and FF-03 require without an external database process |
| Plaintext CAS | Filesystem, content-hash directory layout, atomic rename on commit, hardlinks or symlinks into `node_modules` | Recommended | PR-04's atomic commit is a temp-file-then-rename discipline; pnpm's store is prior art |
| Ciphertext store | Filesystem keyed by ciphertext root under the seed host adapter, with a `redb` index recording holding reason | Recommended | SW-05 requires obligated versus voluntary holdings recorded; under delegation the store is whatever the external client uses and the adapter translates |
| Custody store | OS credential store through `keyring` 4.2.0, updated 2026-08-29, holding a wrapping key; envelope keys, identity keys, and per-entitlement envelopes encrypted under it on disk | Yes | The accepted default: a local keystore under Windows Credential Manager, macOS Keychain, or Linux Secret Service. Credential stores hold small secrets, so the pattern is a wrapping key in the store and an encrypted blob on disk |
| Chain state reads | `alloy` view calls against more than one configured Base RPC endpoint, aggregated and failing closed on disagreement | Yes | XA-06 |
| Envelope recovery | Event and calldata reads from a full-history Base node | Recommended | CD-04; a configured archive endpoint is an operating dependency to state |
| Metrics store | Local append-only metrics under the daemon with the RO-03 schema, exported through the diagnostics API | Recommended | No external metrics service is required by the sources |

## DevOps Tooling

**Fixed.** Signed, atomic, schema-aware, reversible updates. Installation through one Rust coordinator on Windows, macOS, and Linux, with service lifecycle under each platform's service manager or an equivalent persistent user service. The packaged MVP runs without a developer toolchain. The repository ships unit, integration, and end-to-end facilities and every requirement's proof class maps to one. The verifier is deployed to Base Sepolia by the harness.

**Recommended.**

| Concern | Choice | Verified | Note |
| --- | --- | --- | --- |
| Release packaging | `cargo-dist` 0.32.0, updated 2026-05-22 | Yes | Builds per-platform archives and installers for Rust binaries; the Tauri application uses Tauri's own bundler |
| Platform service lifecycle | `systemd` units on Linux, `launchd` agents or daemons on macOS, a Windows Service or a per-user scheduled task where elevation is unavailable | Recommended | SI-06 requires survival across reboot with a user-service fallback; each is a small adapter behind one lifecycle interface |
| Code signing | Apple Developer ID signing and notarization on macOS; Authenticode on Windows; Sigstore `cosign` signatures published alongside every artifact on all three platforms | External context | SI-04 requires authentication before execution; platform signing satisfies the OS gate and Sigstore gives the installer a platform-independent verification path |
| Continuous integration | GitHub Actions with a matrix over the three platforms, running unit, integration, and the clean-machine end-to-end scenarios on ephemeral runners | Recommended | XA-07 requires the full suite on a clean machine; ephemeral runners are the clean machine |
| Local chain for development | Foundry `anvil` | External context | Precedes Base Sepolia in the developer loop |
| Test chain | Base Sepolia | Fixed by the product requirements | The harness deploys the verifier here |
| Contract deployment | Foundry scripts with deterministic addresses recorded in the configuration registry | Recommended | Per-chain contract addresses live in the chain adapter's configuration, not in code |

## Security Tooling

**Fixed.** Every input untrusted until validated at its boundary; fuzzing at every adapter contract; decrypt-capable material memory-only and zeroized at every transition; telemetry scanned for sensitive fields; the Rust verifier and the deployed contract cross-verified bit for bit; external cryptographic review before any priced deployment.

**Recommended.**

| Concern | Choice | Note |
| --- | --- | --- |
| Zeroization | `zeroize` on every type holding a credential, piece-group key, cipher state, or scalar, with `Drop` implementations | CR-07 |
| Constant-time operations | `subtle` for comparisons over secret material; curve arithmetic from libraries that document constant-time scalar multiplication | The pairing libraries below document their timing posture per operation |
| Dependency auditing | `cargo-audit` and `cargo-deny` in CI, with a license allowlist for the source-available posture | Also enforces the licensing decision on the dependency tree |
| Fuzzing | `cargo-fuzz` targets for every adapter boundary, descriptor parser, IPC request, and proof verifier input | XA-01, CR-06 |
| Contract analysis | Foundry's fuzz and invariant testing plus a static analyzer such as Slither in CI | External context for Slither; the mutation and replay vectors are Foundry tests |
| Telemetry scanning | A test that greps every log, trace, metric, and crash artifact produced by the acceptance run for known secret encodings and fails on any hit | RO-03, AS-20 |
| Secret-free diagnostics | Redaction at the `tracing` layer so that secret-typed values cannot be formatted | Type-level enforcement rather than review |
| Signing-key custody | Release signing keys under the same custody discipline as issuance material, held off the CI runner with a rotation path | The non-functional review's NF-S11 gap |

## Shared Libraries

**Fixed primitives.** BLAKE3 with Bao verified streaming for integrity; AES-256-CTR with a 64-bit IV and 64-bit block counter for the payload; Ed25519 at the handshake and content-signing layers; secp256k1 at the EVM chain layer; Type-3 pairing groups on BN254 and BLS12-381 for the credential KEM, envelope, and delivery proof; a domain-separated KDF and hash-to-scalar; W3C DID Documents for the binding schema.

**Recommended Rust libraries.**

| Primitive | Crate | Verified | Note |
| --- | --- | --- | --- |
| BLAKE3 | `blake3` 1.8.7, updated 2026-08-20 | Yes | The reference implementation |
| Bao verified streaming | `bao` 0.13.1, updated 2025-04-07 | Yes | By the BLAKE3 authors; encoding, slicing, and outboard verification for ciphertext, sidecar, and plaintext roots and for random storage challenges. Its release cadence is slower than `blake3`'s and the harness should pin it |
| AES-256-CTR | RustCrypto `aes` and `ctr` | Widely used; not re-verified | The counter layout is the protocol's: IV in the high 64 bits, block index in the low 64, fields not integer addition; the adapter constructs counter blocks itself and uses the crate only for the block cipher and keystream |
| Ed25519 | `ed25519-dalek` | Widely used; not re-verified | With domain separation and complete-message binding supplied by the signature adapter |
| secp256k1 | `k256` from RustCrypto, or `alloy`'s signer which wraps it | Widely used; not re-verified | EIP-712 signing through `alloy` |
| Pairing curves, primary | arkworks: `ark-bn254` 0.6.0 and `ark-bls12-381` 0.6.0, both updated 2026-04-26, over `ark-ec` and `ark-ff` | Yes | One API over both curves, which is exactly what `IPairingAdapter` needs; multi-scalar multiplication and pairing-product evaluation provided; encodings must be adapted to the precompile formats, which is adapter work either way |
| Pairing curves, alternative | `halo2curves` 0.10.0, updated 2026-05-14 | Yes | Also covers both curves with performance-oriented implementations; a second candidate for the harness to benchmark against arkworks |
| BLS12-381 only, not recommended | `blstrs` 0.7.1, last updated 2023-08-14 | Yes | High performance but two years without a release, and it covers one curve; named so it is not rediscovered |
| KDF | HKDF over BLAKE3 keyed mode, using `blake3`'s `derive_key` with the protocol's domain strings | Recommended | Keeps the hash family to one; the specification requires domain separation and names BLAKE3 keyed mode for the keyed plaintext root |
| Hash-to-scalar | BLAKE3 extendable output reduced modulo the group order with a domain tag, per the specification's identifier mapping | Recommended | The exact construction is fixed at the `kdf/hash-to-scalar` ticket and mirrored in Solidity |
| Randomness | `rand_core` with the OS RNG through `getrandom` | Widely used | CR-05 requires a cryptographic source for First Finder lineage |
| DID Documents | `serde`-based types over the DID Core data model | Recommended | The on-chain fields are two storage words; the document is anchored by hash and resolved off chain |

**Recommended Solidity libraries.** A project-owned pairing library over the precompile addresses in both verifier forms, with constants and vectors generated from the Rust reference; OpenZeppelin for ERC-721 and access control, which are conventional; ERC-4337 EntryPoint v0.7 as deployed on Base for the paymaster integration.

## Third-Party Services

**Fixed posture.** Any service the project runs is scaffolding no client depends on: the relayer covers the free path only, the claim verifier is one implementation behind an interface with a revocable key, and the seed host is the first seeder, not a privileged one. Rights-holder outreach is not a service.

**Recommended.**

| Need | Choice | Note |
| --- | --- | --- |
| Base RPC access | More than one provider, or one provider plus a project-run node, configured by default | XA-06 requires reads from more than one node; a single RPC provider is a censorship point the specification names |
| Full-history node for envelope recovery | A provider offering archive access on Base, or a project-run archive node | CD-04 |
| ERC-4337 bundler and paymaster | One of the providers operating on Base, evaluated against per-identity rate-limit controls and cost reporting; the peers' review named Pimlico, Alchemy, and Coinbase's platform as candidates | External context; the relayer adapter must not depend on one provider's API shape |
| Wallet connection | WalletConnect for mobile wallets from any desktop; EIP-1193 for browser-extension and desktop providers; Frame evaluated as the first desktop-native provider, its maintenance status verified first | The custody analysis in the product requirements |
| Claim verification inputs | npm registry maintainer metadata; npm provenance attestations in Sigstore bundle form; GitHub OAuth for repository control | MVP Scope's publisher-proof ordering |
| Artifact signing | Apple and Microsoft signing programs; Sigstore for cross-platform signatures | Required by SI-04 in effect, since unsigned binaries are blocked or warned on two of the three platforms |
| BitTorrent library and external clients | `librqbit` compiled into the owned seed host, Apache-2.0, carried as a soft fork through a `[patch.crates-io]` overlay onto tagged upstream releases with the commit pinned in `Cargo.lock`, hooks submitted upstream, and a recorded hard-fork trigger; the delegated seed-host adapter drives an external client such as rqbit's own application, qBittorrent, or Transmission through its API | Per SW-01 and SW-04; each external client is its own adapter; the release carries the Apache license and NOTICE and marks changed files; the project's conformance clause does not bind library code or upstream contributions |
| Tracker and DHT | Public DHT participation from the owned transport; an optional project-run tracker as one discovery source among several | SW-02; no discovery source is authoritative |
| Sign-in providers | None in the MVP. When the account tier is scoped: OpenID Connect providers for website authentication only, never as a key source; the provider identity may feed relayer rate-limit policy as a Sybil-cost input | MVP Scope, Website, Account, and Remote Head |

## Additional Content

**Why nothing here is a requirement.** The Application Requirements fix languages, runtimes, primitives, standards, and structure, and they say that a later workplan may split or combine implementation units without changing a requirement. A library is an implementation unit. Naming one here records a recommendation and its verification date; the node that first consumes it makes the choice, and the standards that govern that node, not this document, decide whether it conforms.

**What was verified and how.** Twelve crate records were read from crates.io on 2026-09-23 for name, latest version, last update, and repository: `ark-bn254`, `ark-bls12-381`, `blstrs`, `bao`, `keyring`, `librqbit`, `alloy`, `tauri`, `cargo-dist`, `halo2curves`, `blake3`, and `redb`. Crates marked "widely used; not re-verified" are RustCrypto and dalek libraries whose status is well established but which were not fetched this session. Foundry, Slither, Sigstore, OpenZeppelin, the bundler providers, and the wallet providers are external context from general knowledge and from the peers' network review.

**Relationship to the other documents.** The technical approach's adapter table names the MVP implementation behind each interface; this document names the libraries those implementations are built from. The dependency map's harness tickets consume the pairing, hashing, and EVM choices here first. The product requirements' Resolved Positions hold the decisions this document treats as fixed: Base, BLS12-381 primary with BN254 retained, Windows, macOS, and Linux, and the crate-per-adapter-family workspace.
